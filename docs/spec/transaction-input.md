# 交易輸入與匯入 v1

決策來源：[issue #19](https://github.com/NTUyu016/stock-analytic-platform/issues/19)。名詞定義見 [`CONTEXT.md`](../../CONTEXT.md)，資料表綱要見 [`data-model.md`](./data-model.md)，費用與稅費法源見 [`../research/tw-trading-costs-taxes.md`](../research/tw-trading-costs-taxes.md)。

> **本文為什麼存在**：[#9](https://github.com/NTUyu016/stock-analytic-platform/issues/9) 把 Transaction 定為唯一事實來源，於是**漏輸入一筆交易不是「資料舊了」，是「數字錯了」，而且是靜默地錯**。賣掉沒登記，儀表板會繼續用舊股數算市值與損益，不會有任何提示。行情斷線在 [#11](https://github.com/NTUyu016/stock-analytic-platform/issues/11) 已有三態指示器；交易完整性在本文之前一個偵測機制都沒有。

> **隱私聲明**：§2 的計算規則是由一份真實的國泰證券對帳單（50 筆成交）反推並逐筆驗證得出。**本文所有範例數字均為合成**，不含任何實際持股、股數或金額。本 repo 為 public。

## 1. 主要輸入路徑：CSV 匯入

### 決定

CSV 匯入是 v1 的主力路徑。手動表單存在，但它的職責是**匯入補不到的東西**：現金股利、股票股利、`ADJUSTMENT`、以及券商匯出漏掉的成交。

**手動表單不自動試算費用與稅**。費用欄位由使用者填寫，系統可依 §2 的規則提供**預填建議值**，但那是建議不是權威，使用者可以整個改掉。

### 為什麼不是手動表單為主

因為交易量。實測半年 60 筆、年化約 120–150 筆，平均每 2–3 個工作天一筆。這個頻率下手動輸入必然漏，而漏掉的後果如本文開頭所述是靜默的。

### 為什麼表單不試算費用

**試算永遠只是估計，而對帳單給的是真值。**

即使 §2 已經把國泰的計算規則反推到 50/50 零誤差，試算仍會在三種情況偏掉：定期定額走固定 1 元不套公式、最低收費會截斷、以及券商日後調整折讓級距。把試算結果當權威，等於用一個會漂移的近似值取代一個現成的精確值。

更關鍵的是**錯誤的形狀不同**。手填錯了你自己知道；試算錯了看起來完全正常，直到某天對帳對不平才發現，而那時已經錯了幾個月。

## 2. 券商計算規則（由實際對帳單反推）

### 決定

國泰證券（電子下單、現股）的計算規則為：

```
成交金額 = floor(成交股數 × 成交價)              # 元以下無條件捨去
手續費   = max(floor(成交金額 × 費率), 最低收費)   # 元以下無條件捨去
證交稅   = floor(成交金額 × 稅率)                 # 元以下無條件捨去，僅賣出

淨收付 = 買進：−(成交金額 + 手續費)
         賣出： 成交金額 − 手續費 − 證交稅
```

參數（**必須存成帶生效區間的設定，不得硬編碼** —— [#6](https://github.com/NTUyu016/stock-analytic-platform/issues/6) §10.1）：

| 參數 | 值 | 說明 |
|---|---|---|
| 費率 | `0.000399` | 牌告 `0.001425` × 電子下單 2.8 折 |
| 最低收費 | `1` 元 | |
| 定期定額 | 固定 `1` 元 | **不套上面的公式** |
| 證交稅－股票 | `0.003` | |
| 證交稅－ETF | `0.001` | |

### 這解掉了 #6 標為「實作前必須先解掉」的問題

[#6](https://github.com/NTUyu016/stock-analytic-platform/issues/6) §9 第 1、2 項原文是「手續費／證交稅**元以下的進位規則**未見於證交所或券商公開一手文件，需以實際交割單反推」。**本節即為該反推**，答案是**三者皆為無條件捨去**。

### 驗證方法

以上規則對該份對帳單的 **50 筆成交全數吻合，零誤差**，包含：

- 10 筆成交金額帶小數的列，全部驗證了 `floor` 而非四捨五入
- 15 筆賣出的證交稅，14 筆吻合 `0.3%`、1 筆 ETF 吻合 `0.1%` —— **這是 ETF 稅率分流的實證，不再只是法條推論**
- 50 筆淨收付金額全部吻合，無一例外
- 3 筆定期定額不吻合一般公式，但全部吻合「固定 1 元」

實作時**必須把這 50 筆等價的合成案例做成回歸測試**（[#12](https://github.com/NTUyu016/stock-analytic-platform/issues/12) 已規定「錢的計算嚴格 TDD」）。

### 對 #6 的修訂：國泰是即時折讓，不是先收後退

[#6](https://github.com/NTUyu016/stock-analytic-platform/issues/6) §1.3 依永豐金的「次月 15 日退回交割帳戶」推論出一條規格要求：「交易紀錄模組必須分開記錄『交割時扣款額』與『淨手續費』兩個欄位，否則對帳會對不起來」。

**對國泰不成立。** 對帳單上的手續費已經是折讓後金額，淨收付金額也直接用它算，50 筆零誤差。**折讓在成交當下就生效。**

因此 v1 **不需要**那兩個欄位。若日後接入採先收後退的券商，再回頭加。

### 未證實的假設（三項）

誠實記錄，因為它們影響實作但資料不足以證明：

| # | 假設 | 證據 | 避險做法 |
|---|---|---|---|
| 1 | 費率是 `0.000399`（2.8 折） | 反推區間為 `[0.00039893, 0.00040029)`，2.8 折落在其中 | **`0.0004` 也落在同一區間，50 筆無法區分**。取 2.8 折是因為券商牌告佐證。費率既然是設定值，改動成本為零 |
| 2 | 委託書號逐日回收 | 50 筆橫跨 7 個月無碰撞 | 樣本不足以證明全域唯一。**自然鍵加上成交日**（見 §6），成本為零 |
| 3 | 委託書號前綴 `p0` 代表定期定額 | 該前綴 5 筆手續費皆為 1 元，與牌告吻合 | 無券商文件佐證。**不拿它做任何自動歸屬**（見 §7） |

## 3. 國泰對帳單格式的十個陷阱

每一項都會讓 parser 靜默出錯，因此每一項都必須有對應的處置。

| # | 陷阱 | 處置 |
|---|---|---|
| 1 | **匯出被分頁截斷**。首行寫「總計有 N 筆資料，當前資料為 1-M 筆」，`M < N` 時檔案不完整 | **解析首行並在 `M < N` 時擋下整批匯入**，明確告知缺 `N−M` 筆。見 §9 |
| 2 | 首行是中文說明，**表頭在第 2 行** | 跳過首行後再讀表頭 |
| 3 | **只有中文股名，沒有股票代號** | 見 §5 反查流程 |
| 4 | **沒有市場別欄位**，上市與上櫃混在同一份 | 反查時一併決定 `market` |
| 5 | 「成本」欄是**單筆成交總額**，不是本專案的 Cost Basis | 映射為成交金額。**詞彙衝突已記入 `CONTEXT.md`** |
| 6 | 數字帶千分位逗號並以引號包覆；日期為 `YYYY/MM/DD` | 正規化 |
| 7 | 買賣別是中文 `現買`／`現賣`；信用交易欄位存在但值為 0 | 見 §10 |
| 8 | **完全沒有股利與除權息列** | 結構性缺漏，只能靠 §8 補 |
| 9 | 委託書號在單日內唯一 | 作為自然鍵的一部分，見 §6 |
| 10 | **同日、同標的、同股數、同價格的兩筆不同委託確實會出現** | 因此**除委託書號外無任何欄位組合可去重**。這不是假想案例，實際對帳單中就有 |

> **陷阱 1 的二階風險**：偵測依賴首行那句中文的格式。若國泰改寫該句，偵測會失效且無聲。因此規則是——**首行無法依預期格式解析時，發出明確警告並在匯入摘要中標示「完整性未經驗證」**，不可視為通過。

## 4. 中性匯入格式

### 決定

除國泰 parser 外，另定義並**公開**一個中性 CSV 格式，可直接上傳。

### 為什麼這不是額外功能

匯入流程無論如何都是：

```
券商格式 → 中間表示 → 反查 / 去重 / 驗證 / 衝突提示 → 落地
```

後三段是所有來源共用的邏輯，因此**那個中間表示在程式碼裡必然存在**。把它的 schema 寫成文件並開放上傳，邊際成本接近零。

這與 [#12](https://github.com/NTUyu016/stock-analytic-platform/issues/12) 對行情源的判斷是同一條：#12 把「adapter 必須從第一天就可換源」列為硬性要求，理由是 v1 用 Fugle 但可預見要換 Shioaji。**交易匯入源的處境完全相同** —— 目前只有國泰，但那是「目前唯一」不是「永遠唯一」。兩處採用不同標準需要理由，而此處沒有。

它另外買到兩件事：parser 因券商改格式而壞掉時有退路；以及**能匯入國泰帳戶開立之前的舊交易**，那些資料券商永遠不會給。

### 欄位規範

| 欄位 | 必填 | 說明 |
|---|---|---|
| `traded_on` | ✅ | `YYYY-MM-DD` |
| `type` | ✅ | `BUY` / `SELL` / `CASH_DIVIDEND` / `STOCK_DIVIDEND` / `ADJUSTMENT` |
| `symbol` | ✅ | 標的代號。**用代號不用中文名** |
| `market` | | 省略時由 `symbol` 反查；跨市場撞號則中斷 |
| `quantity` | 依 `type` | |
| `price` | 依 `type` | 每股價格，原幣別 |
| `fee` | | 省略視為 0，**但列入匯入摘要的警告** |
| `tax` | | 同上 |
| `cash_amount` | 依 `type` | `CASH_DIVIDEND` 用 |
| `currency` | | 省略時取自標的 |
| `external_ref` | | 有值則參與去重；空白則每次匯入都視為新列 |
| `note` | `ADJUSTMENT` 必填 | |

**`fee`／`tax` 空白視為 0 但要警告**，是因為「確定沒有費用」與「不知道費用」在數值上無法區分，而後者會讓成本基礎偏低。系統不猜，但也不能讓它無聲通過。

## 5. 標的反查：alias → OpenAPI → 中斷問人

### 決定

查詢順序**固定為**：

1. **查已落地的券商簡稱對照**（`instrument_provider_symbol`）
2. 未命中 → 打官方 OpenAPI 反查
3. 唯一命中 → 自動建立 `instrument` 與對照，繼續
4. **查無或多筆命中 → 中斷整批匯入**，列出待指定的名稱

### 為什麼對照表優先於 API，而不是反過來

直覺會想「先打 API 拿最新的」。**這是錯的。**

API 回的是**今日快照**（[#3](https://github.com/NTUyu016/stock-analytic-platform/issues/3) 已證實這些端點無查詢參數、僅最新一期），它會隨市場變動漂移；對照表是**凍結的歷史事實**。當公司改簡稱後，API 開始回新名字，而你手上的舊對帳單寫的是舊名字 —— 這時只有對照表救得了你。

### 三種會讓自動反查失效的情況

1. **標的已下市** —— 端點只有最新快照，舊對帳單裡的它今天查不到
2. **公司改簡稱** —— 舊名字永遠查不到
3. **停牌** —— 當日可能不在行情檔內

三者都由「中斷並要求人工指定，指定結果永久落地」承接。指定過一次之後，該名稱進入對照表，往後不再依賴 API。

### 不需要新表

沿用 [#9](https://github.com/NTUyu016/stock-analytic-platform/issues/9) 既有的 `instrument_provider_symbol`：把券商當成一個 `provider`（`cathay_statement`）、中文簡稱當成它的 `provider_symbol`。連 `UNIQUE (provider, provider_symbol)` 都正好給出「一個券商簡稱只能對到一支標的」的保證。

該表當初是為了「換行情源不動資料庫」而設計，剛好接得住這個未預料的用途。

### 資料源與可行性

| 市場 | 端點 |
|---|---|
| 上市（含 ETF） | `https://openapi.twse.com.tw/v1/exchangeReport/STOCK_DAY_ALL` |
| 上櫃 | `https://www.tpex.org.tw/openapi/v1/tpex_mainboard_daily_close_quotes` |

實測合計 **11,572 個簡稱、零撞名**，且對該份對帳單的 14 個股名 **14/14 全數解析成功**。

> 不使用 `opendata/t187ap03_L`（上市公司基本資料）—— 它只涵蓋**公司**，ETF 是受益憑證不在其中。
>
> 授權：兩個端點均適用[政府資料開放授權條款第 1 版](https://data.gov.tw/license)，可商用可散布，**但須顯名標示來源**（[#3](https://github.com/NTUyu016/stock-analytic-platform/issues/3) §授權）。

### ⚠️ 實作注意：憑證驗證

實測在 **Windows 上的 Python** 存取這兩個端點會失敗於 `SSL: CERTIFICATE_VERIFY_FAILED — Missing Subject Key Identifier`，而同一台機器上的 `curl` 正常。這是本機憑證庫的問題，Linux 容器（[#12](https://github.com/NTUyu016/stock-analytic-platform/issues/12) 選定的部署環境）預期不受影響。**但本地開發會撞到**，需在開發文件中記錄。

## 6. 去重與衝突

### 決定

- 去重自然鍵：**`(券商, 成交日, 委託書號)`**，以 `transaction.external_ref` 落地
- 重複匯入同一份檔案 → 自然鍵已存在的列**靜默跳過**
- 自然鍵相同但數值不同 → **視為衝突，中斷並列出差異**，不覆寫
- 與**無 `external_ref` 的手動列**疑似重複 → **只提示，由使用者逐筆決定**

### 為什麼鍵裡要有日期

委託書號在單日內唯一是確定的；跨日全域唯一是**未證實的假設**（§2）。台股委託書號傳統上為 5 碼且逐日回收。加上日期的成本是零，賭錯的代價是**靜默吃掉一筆真交易**。

### 為什麼不自動合併手動列

因為**同日、同標的、同股數、同價格的兩筆不同委託確實會發生**（§3 陷阱 10），實際對帳單中就有一組。這證明了「看起來相同」不等於「就是同一筆」。

自動合併會在某天悄悄刪掉一筆真交易 —— 而那正是本文開頭要防的靜默錯誤。**用一個靜默錯誤去修另一個靜默錯誤是淨虧。**

### 匯入的原子性

**全成功或全不進。** 任何反查失敗、衝突、或格式違規都讓整批不落地。

不做「跳過壞列繼續」的理由是：一個進了一半的帳本**看起來是正常的**，損益數字照算照顯示，只是錯的。中斷至少讓你知道匯入沒完成。

## 7. Portfolio 歸屬

### 決定

匯入時**整批指定**一個目標 Portfolio。事後可在交易明細頁逐筆或批次搬移。**不依委託書號前綴自動分類。**

### 為什麼

券商對帳單是一個證券帳戶的流水，**沒有任何欄位對應到使用者心中的帳本分類**。而 `CONTEXT.md` 定義同一支 Instrument 在不同 Portfolio 是兩個各自獨立計算成本的 Position —— 歸屬錯了，每股成本就錯了。

委託書號前綴看似能區分通路（例如疑似定期定額的前綴），但那個語意是**逆向推論、無券商文件佐證**（§2 假設 3）。拿一個猜出來的代碼去決定成本計算的歸屬，錯了會靜默算錯。

前綴可以當**搬移時的篩選建議**，那是提示不是自動決定，與 §6 的處理原則一致。

## 8. 公司行動

### 決定

| 事件 | 處理 |
|---|---|
| **除權息** | 盤後排程比對持有標的與官方預告，命中則產生**待確認項**；使用者確認或修改金額後才寫入 `transaction` |
| **減資、換股、合併** | 手動 `ADJUSTMENT` |

### 為什麼只有除權息自動化

三個條件同時成立才值得自動化，除權息三個都中：

1. **頻率高** —— 長期持有取向下每年每檔都會遇到
2. **有官方資料源** —— 見下
3. **不做就會靜默出錯** —— 它是**使用者沒做任何動作、但股數與成本自己變了**的事件。CSV 永遠不會提醒你，因為對帳單裡根本沒有這種列（§3 陷阱 8）

減資與換股一年難得一次、沒有乾淨的官方 feed（[#3](https://github.com/NTUyu016/stock-analytic-platform/issues/3) 已將 MOPS 列為不建議程式化存取），而 `CONTEXT.md` 已把 `ADJUSTMENT` 定義為「刻意保留的逃生門」—— 那就讓它當逃生門。

### 資料源

| 市場 | 端點 |
|---|---|
| 上市除權息預告 | `https://openapi.twse.com.tw/v1/exchangeReport/TWT48U_ALL` |
| 上櫃除權息預告 | `https://www.tpex.org.tw/openapi/v1/tpex_exright_prepost` |

實測上市端點回 122 筆，含 `Exdividend`（息／權）、`CashDividend`、`StockDividendRatio`、`SubscriptionPricePerShare`。

排程搭在 [#9](https://github.com/NTUyu016/stock-analytic-platform/issues/9) 既有的「每日盤後追一筆 `daily_close`」上，不新增排程元件。

> ⚠️ 端點同樣只有最新快照，**漏跑一天就漏掉那批事件**。排程失敗必須留下紀錄並在資料新鮮度指示器上反映（§9）。

### 為什麼必須「待確認」而不能直接落地

**算出來的值必然對不上實際入帳。**

- 實測端點中存在**已公告除息日、但金額欄位為空**的列 —— 這種情況連預填值都沒有
- [#6](https://github.com/NTUyu016/stock-analytic-platform/issues/6) §9 列出股務代理現金股利匯撥手續費（市場常見約 10 元）**未查證**
- 二代健保補充保費 2.11% 會在單次給付達 2 萬元時扣繳，實際入帳為淨額
- 零股配息的取位規則未查證

### 為什麼另立表，而不是在 `transaction` 加 `status`

**加 `status` 會讓每一個查詢都必須記得寫 `WHERE status = 'confirmed'`，而漏寫不會有任何錯誤訊息** —— 只會讓未確認的股利偷偷混進損益與成本基礎。

這正是 [#10](https://github.com/NTUyu016/stock-analytic-platform/issues/10) 對 `user_id` 提出的同一個警告，也是 [#9](https://github.com/NTUyu016/stock-analytic-platform/issues/9) 核心原則第 5 條的形狀。

另立 `pending_action` 表則讓 `transaction` 維持「**裡面每一列都是事實**」的不變量，確認時才 INSERT 過去，**現有查詢一行都不用改**。

## 9. 漏輸入偵測與資料新鮮度

### 決定

三層偵測，收斂成**單一指示器**：

| 層 | 機制 | 抓到什麼 |
|---|---|---|
| 1 | **分頁截斷偵測** —— 解析對帳單首行的總筆數與當前範圍 | 匯出不完整。**完美偵測**（檔案自己招了） |
| 2 | **負股數偵測** —— 推導 Position 出現負股數即報錯 | 漏了買進且後續賣超的情況 |
| 3 | **庫存股數對帳** —— 使用者貼上券商庫存股數，系統比對推導出的 Position | 漏匯期間、反查錯誤、股票股利漏登 |

### 為什麼只對股數，不對均價

**股數是整數且無歧義；均價有定義分歧。**

[#6](https://github.com/NTUyu016/stock-analytic-platform/issues/6) §4.2、§5.2 已指出券商的均價實務慣例與本專案的加權平均定義未必一致（股利要不要沖減成本就是 #6 的「雙軌」問題）。拿它對帳會產生**永遠對不平的雜訊**。

而永遠亮著的警告等同沒有警告 —— 這是 [#11](https://github.com/NTUyu016/stock-analytic-platform/issues/11) 為「非交易時段不用警告色」所定下的原則，此處是同一條理由的第二次適用。

均價仍可**並列顯示供人眼比對**，但不參與「平／不平」的判定。

### 對帳存什麼

只存**比對結果的稽核紀錄**：對帳時間、基準日、平／不平、差異明細。

**不存庫存本身** —— 那等於偷偷建了 [#9](https://github.com/NTUyu016/stock-analytic-platform/issues/9) 明令不做的 `position` 表。存比對結果則不構成事實來源，因為它是一個**已發生的比對事件**，不是可推導狀態的快照。

### 資料新鮮度指示器

單一指示器，同時表達「距上次成功匯入幾天」與「上次對帳結果」。

**不拆成兩個燈**，因為它們回答的是同一個問題：「我的資料現在可不可信」。拆成兩個只會讓兩個都不被看。

### 補登可見性：做前瞻，不做回顧

`traded_on` 與 `created_at` 的落差即補登時長，但**只用於前瞻提示，不在績效頁標示補登區間**。

差別在於可否行動。「你已 N 天沒匯入」是現在能處理的；「這段歷史是事後補的」是一件你改變不了的往事。

而且 [#9](https://github.com/NTUyu016/stock-analytic-platform/issues/9) 的重算模型保證了**補登之後歷史就是對的** —— 那段曲線與即時輸入的一樣可信。標示它反而暗示它較不可信，製造沒有根據的疑慮。又因為 `created_at` 永遠不會變，**該標示會永久掛著**。這是「永遠亮著等於沒有」原則的第三次適用。

## 10. 交易型態範圍：v1 只支援現股

### 決定

買賣別非現股、或任何信用交易欄位非 0 → **中斷整批匯入並指出是哪一列**。不跳過、不推測。

### 為什麼

**當沖證交稅 0.15% 與一般 0.3% 差一倍。** 猜錯不是小數點問題，是成本直接錯一倍。

而且 [#6](https://github.com/NTUyu016/stock-analytic-platform/issues/6) §2.3 指出當沖減半是「**2027-12-31 落日 + 限現款現券 + 限股票（ETF 不適用）**」的三重條件組合 —— 那是一整套規則不是一個係數，**半套實作比不實作危險**。融資融券另有利息、保證金與擔保品，成本模型是另一個東西。

### 現況佐證

該份對帳單 50 筆全為現股（融資金額、資自備款、利息、券手續費四欄皆為 0），15 筆賣出的證交稅**全部**吻合 0.3%／ETF 0.1%，**無一筆為 0.15%**。7 個月零筆當沖。

日後若開始當沖或信用交易，本節即為需要重開的決策點。

## 12. 驗收標準

v1 的交易輸入被視為完成，當且僅當：

1. 丟入未經修改的國泰對帳單 CSV，能完成匯入或給出**明確可行動的中斷原因**
2. §2 的計算規則有等價的合成回歸測試，涵蓋整股、零股撞最低收費、定期定額、ETF 稅率、賣出三項扣除
3. 同一份檔案匯入兩次，第二次**零新增列**
4. 檔案被分頁截斷時**必定擋下**，並指出缺幾筆
5. 出現未知股名時**中斷**，指定一次後再匯入即自動通過
6. 推導 Position 出現負股數時**必定報錯**，不顯示負部位
7. 中性格式 CSV 可獨立完成一次匯入，不依賴任何券商 parser
8. 儀表板能回答「我的資料多久沒更新、上次對帳平不平」
