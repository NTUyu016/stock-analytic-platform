## 0. 這張票的緣起與一句話的問題

#16 定案時撞到一個沒人預料的事實：**0050 於 2025-06-18 一拆四**（188.65 → 47.16），而忽略它的代價是 **CAGR 從 14.609% 掉到 7.934%**（6.7 pp/年），**且 47.57 是完全合法的價格，`numeric(20,8)` 收得下，不會有任何錯誤訊息**。

#16 只綁定了最小要求（盤後排程必須偵測分割並產生 `pending_action`），把型別、峰值調整與參數留給本票。

## 1. 型別：新增具名 `SPLIT`

### 1.1 決定

**`transaction.type` 新增列舉值 `SPLIT`**，語意嚴格定義為：

> **依一個比率改變股數，且沒有任何現金流、總成本基礎不變的事件。**

涵蓋 TWSE 的三種公告類型：**分割、反分割、變更股票面額**。**不涵蓋減資**（理由見 §3）。

**同時新增 `transaction.ratio` 欄位，且它是第一類值，不從股數變化反推。**

### 1.2 為什麼三種公告類型可以共用同一個型別

因為 **TWSE 對三者用的是同一條公式**（`corporate-actions-datasources.md` §2.1，逐字引用自 TWSE 官方頁面）：

> 恢復買賣參考價 = 停止買賣前最後收盤價 / 分割（反分割）比率

**分子沒有任何扣項**，所以 `before_price / after_price` **在定義上就是比率本身**——這是恆等式，不是「實測發現大致相等」的經驗規律。這一點很重要：它讓「跨標的交叉驗證」這個原本掛在簡報上的疑慮直接消失，不需要再多測幾檔。

FinMind 的 `TaiwanStockSplitPrice` 也把三者放在同一張表裡（`type` 欄分別為 `分割`／`反分割`／`面額變更`），**這不是 FinMind 的分類選擇，是 TWSE 本來就用同一套參考價機制處理它們**。

### 1.3 為什麼不繼續用 `ADJUSTMENT` 逃生門

`CONTEXT.md` 明訂 `ADJUSTMENT` 是「**刻意保留的逃生門**，不是資料錯誤的修補工具」，用於「系統未內建專屬邏輯的公司行動」。

分割**不符合這個定義**：它是**已知、可偵測、會反覆發生**的事件——2026-08-09 的查證顯示 `TaiwanStockSplitPrice` 全市場 **32 筆事件**、其中 `6548` 與 `8932` 各發生過**兩次**。把一個有官方公式、有免費資料源、會重複發生的事件長期塞在逃生門裡，逃生門就不再是逃生門了。

**更具決定性的理由是待決 2**：`ADJUSTMENT` 只有 `quantity`／`cash_amount`／`note`，**比率無處可放**。走逃生門的話，`peak_price` 調整所需的比率只能從 `note` 自由文字解析、或從股數變化量反推——而**從股數反推會在有零股或曾經加碼的部位上出錯，且不會報錯**。

### 1.4 `ratio` 的設計（四條硬性規則）

**（a）`CHECK` 必須是雙向的，不可只寫單向**

```sql
CHECK ((type = 'SPLIT') = (ratio IS NOT NULL))
CHECK (ratio IS NULL OR ratio > 0)
CHECK (type <> 'SPLIT' OR quantity IS NULL)   -- 見 §1.5
```

**不可以寫成 `CHECK (type <> 'SPLIT' OR ratio IS NOT NULL)`。** 那個寫法允許非 `SPLIT` 的列填入 `ratio`，而那正是 #15 已經識別過的形狀：**`CHECK` 對不該有值的欄位放行，不會有任何錯誤訊息**。雙向等式讓兩個方向都被擋住。

**（b）語意固定為「新股數 = 舊股數 × ratio」**

| 事件 | `before/after` | `ratio` | 股數 | 峰值 |
|---|---|---|---|---|
| 1 拆 4（0050, 2025-06-18） | 188.65 / 47.16 | **4** | ×4 | ÷4 |
| 4 合 1（反分割，如 00673R） | 7.02 / 28.08 | **0.25** | ×0.25 | ÷0.25 |
| 面額 10 元改 1 元（6548, 2019-09-09） | 312.0 / 31.2 | **10** | ×10 | ÷10 |

**同一個公式同時涵蓋兩個方向**，實作不需要分支。

**（c）寫入的 `ratio` 必須是使用者確認過的乾淨值，不得直接存浮點商**

`after_price` 是**四捨五入後的公告值**：0050 的 `188.65 / 47.16 = 4.00021...`，而官方公告白紙黑字寫的是「除上分割比率（**4** 倍）」。系統在產生 `pending_action` 時把浮點商四捨五入成最接近的簡單比率作為預填值，**由使用者在確認畫面上看到並可修改**，寫入 `transaction.ratio` 的是確認後的值。

> **既有文件的一個小修正**：`tw-benchmark-and-fx-sources.md` §B.4 記的「比例 188.65/47.16 = 4.0002」是正確但迂迴的算法——**官方直接給了整數 4，不需要反推**。

**（d）新股數必須是整數，不是就中斷**

台股現股不存在小數股。若 `舊股數 × ratio` 不是整數，**中斷並要求使用者依實際對帳單輸入**，不得自行捨入。這比照 #19 對當沖與信用交易的既有做法：**看不懂的東西中斷問人，不猜**。

### 1.5 ⚠️ `SPLIT` 怎麼進入部位推導：**`ratio` 是唯一權威，`quantity` 必須是 NULL**

> **這一節是 2026-08-09 的冷讀驗收（#18）撞出來的，它推翻了本文初版的設計。**

本文初版讓 `SPLIT` 同時帶 `quantity`（股數增減量）與 `ratio`，讓它能沿用 `performance.md` §8.1 的不等式聚合 `SUM(signed_qty) FILTER (traded_on <= D)`。**那是錯的，而且錯法正好是本專案最怕的那一種。**

**失效情境**：確認 0050 一拆四時，系統依「當下的股數」算出 delta（持有 1,000 股 → `quantity = +3,000`）。日後**補登一筆分割日之前的舊 `BUY`**（`transaction-input.md` §1 已證實補登是常態，不是例外）——那筆 `+3,000` 永遠不會被修正，而 `performance.md` §8.5「重算保證補登後歷史自動正確」的承諾在此處**靜默失效**。

> 換句話說：**把分割存成 delta，等於把它變成一個快照。** 而 #16 拒絕 `portfolio_snapshot` 的決定性理由正是「歷史隨時會被補登改寫」——實測快照版有 57% 的曲線靜默地錯。**同一個錯誤不能因為換了一張表就被接受。**

**決定**：

> **`SPLIT` 只帶 `ratio`，`quantity` 必須是 NULL。部位推導改為「比率縮放的不等式聚合」。**

```sql
-- 標的 I 在 Portfolio P、日期 D 的股數
SUM(
  t.signed_qty * (
    -- t 之後、D 之前發生的所有分割比率的乘積
    PRODUCT(s.ratio) WHERE s.traded_on > t.traded_on AND s.traded_on <= D
  )
) FILTER (WHERE t.traded_on <= D AND t.type <> 'SPLIT')
```

**三個必須寫對的細節**：

1. **是 `s.traded_on > t.traded_on`，嚴格大於。** `SPLIT.traded_on` 的語意是**恢復買賣日**（§4.6），**那天的交易已經是分割後的股數**，不可再乘一次。用 `>=` 會讓恢復買賣當日的買進被重複放大四倍，而金額看起來完全正常。
2. **這條寫法仍然符合 §8.1 的硬性規則**——它是不等式聚合，沒有 join 任何日曆。§8.1 禁止的是等值 join，不是禁止乘法。
3. **成本基礎同步縮放**：分割不改變總成本，所以**每股成本除以 `ratio`**。若只縮放股數不縮放均價，未實現損益會在分割當天憑空跳動四倍，**而它是一個完全合法的數字**。

⚠️ **不得用 `exp(sum(ln(ratio)))` 實作乘積聚合。** PostgreSQL 沒有內建的 `numeric` 乘積聚合，而 `exp`/`ln` 走 `double precision`——1,000 股經過一次 4 倍分割會算出 `3999.9999999999995`。**股數是錢的計算的一部分**，`tech-stack.md` §7 已定它走嚴格 TDD 且用 `numeric`。正確做法是自訂一個 `numeric` 乘積聚合，或在應用層用 `Decimal` 相乘（分割事件稀少，取回清單相乘的成本可以忽略）。

**這條規則帶來的回歸測試**（已列入 §8）：建倉 1,000 股 → 分割 `ratio=4` → 補登一筆分割日**之前**的 `BUY` 500 股 → 今日股數必須是 `(1000+500)×4 = 6,000`，不是 `1000×4+500 = 4,500`。

### 1.6 順帶補上：`transaction.type` 必須有 `CHECK` 列舉

簡報 §1.1(c) 發現的規格層級不一致：`alert.rule_type` 明文規定要有 `CHECK` 列舉（#15），`transaction.type` 只在說明欄列出五個值、沒有規定 `CHECK`。**本票補上：`transaction.type` 也要有 `CHECK` 列舉。**

理由不是對稱美感，是**填入未知值時要在 `INSERT` 當下就爆，而不是在半年後某張報表裡以「這筆交易怎麼沒被算到」的形式出現**。

### 1.7 但 `CHECK` 擋不住真正的風險，所以另有一條規則

`CHECK` 保證「不會有非法的 type 值」，**但擋不住「某段程式碼只枚舉了 `BUY`/`SELL`，忘了 `SPLIT`」**。那是 #19 拒絕 `transaction.status` 時點名的同一種靜默失效。

**因此規定**：所有依 `transaction.type` 分支的程式碼**必須是窮舉式的**（`match` 加上明確的 `case _: raise`），**不得有靜默的 fall-through 或 `else: pass`**。新增列舉值時，未更新的分支點會在測試中直接拋例外。列為 §8 的測試項。

## 2. `alert_state.peak_price` 的分割調整

### 2.1 決定

**追蹤停損的峰值在 `SPLIT` 生效日除以 `ratio`。**

```
new_peak = old_peak / ratio
```

**觸發源是已確認的 `SPLIT` transaction，不是 FinMind dataset。**

### 2.2 為什麼不直接由 dataset 觸發

`alerts.md` 已定「**峰值可重建，且必須有重建路徑**」。把觸發源綁在 `transaction` 上，重建路徑就是「掃 `transaction` + `daily_close`」——與 #16「Transaction 為唯一事實來源」一致，且**不需要在重建時重新去打一次外部 API**。

若綁在 dataset 上，重建結果會取決於「重建那一刻 FinMind 回了什麼」，那不是可重現的計算。

### 2.3 這填的是 #15 明文留下的缺口

`alerts.md` §4 已記錄：除權息的峰值調整走 `TaiwanStockDividendResult` 的 `reference_price / before_price`，而**分割在 `TaiwanStockSplitPrice`，是另一個 dataset，走不到那條路徑**，並明寫「本規格暫不修改，型別與調整規則另開票處理」。

失效模式 #15 已經用真實數據驗證過，**與除權息完全同形**：峰值停在 188.65 而股價已是 47.57，規則**永久黏在「已觸發」且不報錯**。

### 2.4 未確認期間怎麼辦（這是本節真正困難的部分）

**分割被偵測到、但使用者還沒確認的那段時間，`peak_price` 與 `daily_close` 是不一致的**——價格已經除以 4，峰值還沒有。

三個選項裡，**兩個都是錯的**：

| 做法 | 為什麼不行 |
|---|---|
| 照舊評估規則 | 峰值 188.65 vs 現價 47.57，**追蹤停損立刻觸發並發 Discord**。使用者收到一個完全錯誤的警示 |
| 先斬後奏（不等確認就調整峰值） | 那等於承認「系統可以在使用者沒確認時改他的數字」，而股數卻沒改——**兩個數字用不同的真相**，比全錯更難查 |

**決定採第三條**：

> **只要某個標的存在「未確認、且會改變股數」的 `pending_action`，該標的所有依賴股數或峰值的警示規則一律暫停評估，並在規則面板上標示暫停原因。**

**為什麼**：這是 #14 已確立的原則「**資料不足一律明說不給結論，不硬湊**」在警示上的直接適用，也與 #14「評等被下修時必須標註原因，不可只改數字不說明」同形。**暫停並說明**比「用錯的數字給一個看起來正常的答案」誠實得多。

**判準是行為，不是嚴重度等級**：暫停與否取決於「這個未確認項會不會改變股數」，而不是取決於某個 `severity` 欄位。因此：

| 未確認項 | 是否暫停該標的的規則 |
|---|---|
| `SPLIT`（分割／反分割／面額變更） | **是** |
| 股票股利（`STOCK_DIVIDEND`） | **是**（也改股數） |
| 現金股利（`CASH_DIVIDEND`） | 否（不改股數） |
| 減資 | **是** |
| 匯入衝突（`IMPORT_CONFLICT`） | 視該筆是否改變股數而定 |

**明確不做的事：不在 `pending_action` 加 `severity` 欄位。** 一個「嚴重度」欄位會被隨手填、也會被隨手忽略；而「會不會改股數」是一個從 `kind` 與 `proposed` 就能客觀算出來的判斷。**用行為表達嚴重度，不要用數字表達。**

## 3. 減資與換股：不共用同一套機制

### 3.1 決定

| 事件 | 型別 | 偵測 | 輸入 |
|---|---|---|---|
| 分割／反分割／面額變更 | **`SPLIT`**（具名） | **自動**，且預填比率 | 確認即可 |
| **減資** | `ADJUSTMENT`（維持） | **自動偵測「發生了」，但不預填比率** | **手動，依對帳單** |
| **換股／合併** | `ADJUSTMENT`（維持） | **無**（沒有資料源） | 手動 |

### 3.2 減資：#19 的結論維持，但支撐它的理由被推翻了，換成一個更強的

`transaction-input.md` §8 原文說減資與換股「一年難得一次、**沒有乾淨的官方 feed**」。**2026-08-09 的查證顯示這句話對減資不成立**：

> FinMind `TaiwanStockCapitalReductionReferencePrice` **免費層可用**（需帶 `data_id`），欄位名可**逐字對回 TWSE 英文版頁面**（`PostReductionReferencePrice` ↔ 官方 "Post-Reduction Reference Price"），實測回溯逾十年。

**但結論仍然是「手動輸入」，理由換成一個比原本更強的**：

TWSE 對減資公布的是**三條不同的公式**（`corporate-actions-datasources.md` §3.3，逐字引用）：

> 恢復買賣參考價＝（停止買賣前收盤價 − 息值 − **每股退還股款**）/（減資換股率）　【退還股款】
> 恢復買賣參考價＝（停止買賣前收盤價）/（減資換股率）　【彌補虧損】

**退還股款型減資的分子有扣項，所以 `before/after` 混入了現金退款，不是股數比率。** 實測：

| 標的 | 類型 | before → after | `before/after` | 真正的換股率倒數 |
|---|---|---|---|---|
| 6116 彩晶 | 彌補虧損 | 1.69 → 3.38 | 2.0000 | 2.0 ✅ 相符 |
| 2603 陽明 | 現金退還 | 80.8 → 187.0 | **2.3144** | **2.5** ❌ 不符 |
| 2409 友達 | 現金退還 | 14.7 → 15.87 | **1.0796** | **1.25** ❌ 不符 |

**而這個 dataset 沒有任何欄位單獨給出「減資換股率」或「每股退還股款」**——兩者被壓進同一個參考價裡，**從這個 dataset 分離不出來**。

> **這就是為什麼減資不能併進 `SPLIT`。** 若併進去，退還股款型減資會得到一個**「看起來已經修好了」但實際錯的比率**——而依 §2.3 的失效模式，錯的時候不會有任何錯誤訊息。**比完全不做更糟**：完全不做至少會被 #19 的對帳機制抓到股數對不上，而一個錯的自動調整會讓對帳也對得起來（因為股數被改成了錯的值）。

**但偵測仍然自動化**：既然資料源乾淨且免費，盤後排程**應該偵測到「這檔在這天減資了」並產生 `pending_action`**，只是 `proposed` 裡**不預填比率**，而是明白寫「請依對帳單輸入減資後股數與退還金額」。

**這把「偵測」與「推算」分開了**：偵測有乾淨來源（TWSE 公告過），推算沒有（比率算不出來）。把它們綁在一起，會讓「算不出比率」變成「乾脆連提醒都不提醒」，而使用者最需要的其實就是那個提醒。

### 3.3 換股與合併：#19 的判斷完全未被推翻

2026-08-09 掃過三處，**全部沒有**：

- **FinMind 合法 dataset 全清單**（由 API 的 enum 驗證錯誤原樣吐出，93 個）——沒有任何一個對應合併／換股／股份轉換。
- **`openapi.twse.com.tw`（143 paths）**——最接近的 `/company/suspendListingCsvAndHtml` 只有下市日期與公司名，**沒有下市原因、沒有換股比例、沒有存續公司代號**。
- **`www.tpex.org.tw/openapi`（225 paths）**——同樣沒有。

> **換股比例正是重建部位唯一需要的數字**，而它在整個開放授權側不存在。維持手動 `ADJUSTMENT`，`note` 必填。

**作為對照**：除權息在兩邊都有專屬的**預告表**（`/exchangeReport/TWT48U_ALL`、`tpex_exright_prepost`）。分割、減資、換股**都沒有等價物**——這也解釋了為什麼提前示警窗口是本票拿不到的東西（§4.5）。

## 4. 偵測的觸發、範圍與確認流程

### 4.1 掛在既有排程上，不新增元件

比照 #19 對除權息的既有做法：**掛在盤後排程上，不新增排程元件**（`deployment.md` §4）。

**且必須遵守 `deployment.md` §4.1 的回補式硬性規則**：任務語意是「把公司行動補齊到最新交易日」，不是「看今天有沒有」。這在本專案的部署形狀下（電腦會關機）是必要的。

**本票的三個資料源都是歷史型的，回補直接可行**：`TaiwanStockSplitPrice`（全歷史，見 §4.4）、`TaiwanStockCapitalReductionReferencePrice`（實測回溯逾十年）、`TaiwanStockDividendResult`（2003 起）。

> ⚠️ **對照**：除權息的**預告**表（`TWT48U_ALL`、`tpex_exright_prepost`）是**快照型**，補不回來。`deployment.md` §4.1 已規定這類端點必須另走歷史型的結果表補齊——**預告表只用於提前示警，不得作為唯一的偵測來源。** 而分割連預告表都沒有（§4.5），所以它從一開始就只有歷史型這一條路。

### 4.2 一次拉全市場，在本地過濾持股

`TaiwanStockSplitPrice` 是 FinMind 免費層**少數允許不帶 `data_id` 拉全市場**的 dataset（實測全市場全歷史僅 **32 列**，一次請求拿完）。

**因此決定：一次拉全市場，在本地比對持股標的。** 這比逐檔查省 N−1 次請求，而 FinMind 無 token 的額度很緊——實測會回 **HTTP 402（不是慣例的 429）**，且回應標頭**沒有任何 `X-RateLimit-*` 或 `Retry-After`**。

> ⚠️ **這是一個例外，不是通則**：同一族的 `TaiwanStockCapitalReductionReferencePrice` 與 `TaiwanStockDividendResult` 都**必須**帶 `data_id`。因此 adapter 必須同時支援兩種取法，且**退避邏輯要認得 402**——任何「遇到 429 才退避」的實作在這裡會漏接。

### 4.3 ⚠️ 偵測不得用 `type` 欄位過濾

**這是本節最重要的一條規則。**

`TaiwanStockSplitPrice` 的 `type` 欄有四個值，其中一個是**空字串**：

```json
{"date":"2026-03-31","stock_id":"00631L","type":"","before_price":443.15,"after_price":20.14,...}
```

`443.15 / 20.14 = 22.0`——從數字看是一次 1 拆 22 的分割，**但 `type` 是空的**。

> **若偵測邏輯寫成 `WHERE type IN ('分割','反分割','面額變更')`，這一列會被靜默漏掉**，而漏掉一次分割的後果就是 §0 那個 6.7 pp/年。

**因此規定**：

> **偵測的判準是「該列存在，且 `before_price / after_price` 偏離 1 超過 0.5%」，不看 `type` 欄位。** `type` 只作為顯示給使用者的說明文字，不參與任何邏輯判斷。

0.5% 的門檻用來吸收捨入誤差（實測最大約 2×10⁻⁵ 量級），遠小於任何真實的分割比率（最小的是 2）。**這個數字是設定值，不寫死常數**（比照 #6「費率一律不得硬編碼」與 #14 對評等切點的既有做法）。

### 4.4 掃描範圍與已知邊界

| 項目 | 決定 |
|---|---|
| 範圍 | **只處理持股標的**（比照 #19 除權息的既有判斷）。全市場資料照拉（反正一次請求），但只為持股產生 `pending_action` |
| 頻率 | 每個交易日盤後一次，與 `daily_close` 同批 |
| **回溯下限** | **2019-09-09**。實測 `end_date=2019-09-08` 回 0 列——這是 dataset 的實際下限 |

> ⚠️ **2019-09-09 這條線是一個會靜默漏事件的邊界。** 0050 的分割在 2025 年不受影響，但**若日後匯入更早的交易紀錄，那個年代的分割事件這個 dataset 給不出來**，必須人工補。實作時：匯入交易紀錄時若 `traded_on` 早於 2019-09-09，須明白提示這件事，不可假設偵測涵蓋全部歷史。

### 4.5 沒有提前示警窗口（誠實記下）

TWSE 有一張「ETF分割(反分割)**預告表**」，**但它不在開放授權側**（在 `www.twse.com.tw/zh/announcement/*`，屬 #3 已判定的爬蟲禁止側），且 FinMind **沒有對應的 dataset**。

因此：**可程式化取得的只有事後的恢復買賣參考價**。0050 的案例中，停止買賣期只有 **5 個交易日**，而系統最快也要等到恢復買賣當日盤後才會知道。

**這不是設計選擇，是資料源的天花板。** 記在 §7。

### 4.6 `pending_action` 的欄位語意（修訂 #9）

| 欄位 | 分割場合的值 | 備註 |
|---|---|---|
| `kind` | `CORPORATE_ACTION` | 既有值，**不新增列舉** |
| `effective_on` | **恢復買賣日**（`TaiwanStockSplitPrice.date`） | ⚠️ 見下 |
| `proposed` | `{"type":"SPLIT","ratio":4,"before_price":188.65,"after_price":47.16,"source_type":"分割"}` | 減資場合**不含 `ratio`** |
| `source` | `finmind_TaiwanStockSplitPrice` | ⚠️ 見 §7 |

⚠️ **`effective_on` 的欄位註解必須修訂。** `data-model.md` 目前寫的是「除權息**基準日**」。2026-08-09 的查證確立：`TaiwanStockSplitPrice.date` 是**恢復買賣日**（9/9 案例全部成立，TWSE 官方頁面的欄位標籤逐字就是「恢復買賣日期」）。

對 0050 這類 ETF，官方公告白紙黑字「新受益憑證**換發基準日**暨受益憑證終止上市(櫃)日：114年6月18日」——**與上市買賣日同一天**。但對一般個股，《上市公司換發有價證券作業程序》第 3 條把「換發基準日」與「新股上市買賣日」定義成**兩個獨立的日期**，而個股逐案的基準日**不在任何可程式化端點上**。

**因此決定**：`effective_on` 的語意統一定義為「**該事件生效、市場開始以新股數與新價格交易的第一個交易日**」，欄位註解改寫成這句話。理由：這才是**部位推導真正需要的那一天**——`performance.md` 已定「部位推導一律用 `traded_on <= D` 不等式聚合」，而我們要的是「從哪一天起股數變了」。換發基準日是股務作業的日期，對估值沒有作用。

### 4.7 未確認時怎麼辦

使用者定案：**畫面上一直提醒 + Discord 通知**。

| 機制 | 規則 |
|---|---|
| **儀表板常駐區塊** | 待確認項清單常駐於儀表板。**⚠️ 這是 `dashboard-ui.md` 沒有的東西**（#11 只涵蓋警示規則面板），本票新增，見 §6 |
| **Discord 通知** | 偵測當下發一次。**若超過 5 個交易日仍未確認，再發一次**，之後不再重複 |
| **規則暫停** | 見 §2.4——該標的所有依賴股數的警示規則暫停並標示原因 |
| **對帳仍是最後防線** | #19 的對帳「只比股數」抓得到這個錯，但那要使用者**主動觸發**。它是安全網，不是主要機制 |

**為什麼只補發一次而不是每天發**：`transaction-input.md` 已用過這條原則——「**永遠亮著的警告等同沒有警告**」。每天發一次 Discord 的結果是使用者兩週後把這個頻道靜音，那時它就真的失效了。**發兩次（立刻 + 5 個交易日後）已經是這件事值得的注意力上限**；再往上是靠「規則暫停」這個**會影響功能**的後果來確保它不被無視——一個看得到後果的暫停比第十封通知有效。

⚠️ **Discord 通知內文不得含股數、金額或百分比**——#15 已定，理由是 Discord Developer Policy 第 16 條禁止 transmit financial information，且「沒註冊、沒有 Application ID，打 webhook 一樣落在 Application 定義內」。分割通知只寫**標的、日期、事件類型與一個連結**。

## 6. 待確認項的呈現（新增，修訂 #11）

`dashboard-ui.md` 只定義了警示規則面板，**沒有 `pending_action` 的呈現方式**。本票補上最小規格：

- **位置**：儀表板側欄，**只在有未確認項時出現**——沒有待辦時不佔版面。這是 #11「非交易時段用警告色會讓使用者學會忽略它」的同一條原則：**常駐一個永遠是 0 的計數器，等於訓練使用者不看它**。
- **顏色**：依 #11 的硬性規則，**顏色只保留給價格方向**，紅綠不得用於此。待確認項用**琥珀**（與「盤中斷線」同一個「異常但非價格」的色階）。
- **排序**：會改變股數的排前面。這是 §2.4 判準的視覺對應。
- **每一項必須顯示**：標的、生效日、事件類型、系統預填值、以及**「這個項目目前讓什麼功能暫停了」**——最後這項是關鍵，它把「規則暫停」這個後果放在使用者看得到的地方，而不是讓他日後納悶為什麼追蹤停損沒動。

## 8. 必須寫成測試的條目

| # | 條目 |
|---|---|
| 1 | `CHECK ((type = 'SPLIT') = (ratio IS NOT NULL))` 雙向都擋：`SPLIT` 缺 `ratio` 失敗；非 `SPLIT` 帶 `ratio` 也失敗 |
| 2 | `transaction.type` 填入列舉外的值，`INSERT` 失敗 |
| 3 | 所有依 `type` 分支的程式碼為窮舉式：新增一個假的 type 值，**每一個分支點都拋例外**，沒有任何一處靜默通過 |
| 4 | 0050 案例：持有 1,000 股，套用 `ratio=4` 後為 4,000 股，且**分割日前後該檔市值連續**（`performance.md` §8A 不變量 #10） |
| 4a | **補登回歸測試**（§1.5）：建倉 1,000 股 → 分割 `ratio=4` → 補登一筆分割日**之前**的 `BUY` 500 股 → 今日股數必須是 **6,000**，不是 4,500 |
| 4b | **恢復買賣當日的買進不得被再乘一次**：分割日當天買 100 股，今日股數 = `1000×4 + 100 = 4,100`，不是 4,400 |
| 4c | **每股成本同步縮放**：分割前後該檔的**未實現損益不變**（總成本不變、市值連續） |
| 4d | 乘積聚合走 `numeric`：`1000 × 4` 必須恰為 `4000`，不得出現 `3999.9999999999995` |
| 5 | 反分割案例：`ratio=0.25`，股數與峰值方向正確（同一條公式，不分支） |
| 6 | `peak_price` 在 `SPLIT` 生效日除以 `ratio`；峰值重建（從 `transaction` + `daily_close` 重跑）得到相同結果 |
| 7 | **`type` 為空字串的那一列仍被偵測到**（`00631L` 2026-03-31，比值 22.0）——用真實資料當 fixture |
| 8 | 存在未確認的改股數 `pending_action` 時，該標的的追蹤停損**不評估、不發通知**，且面板顯示暫停原因 |
| 9 | 存在未確認的**現金股利** `pending_action` 時，該標的規則**照常評估**（判準是會不會改股數） |
| 10 | 減資的 `pending_action` 的 `proposed` **不含 `ratio`** |
| 11 | `舊股數 × ratio` 非整數時中斷，不自行捨入 |
| 12 | 退避邏輯認得 **HTTP 402**（不只 429） |
