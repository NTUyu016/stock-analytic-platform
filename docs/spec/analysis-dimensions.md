## 0. 六維定案（待決事項 1 + 2）

### 決定

放棄舊碼「八維」框架，改為六維，且維度數與資料來源是同一次決策的兩面：

| 維度 | 資料來源 | 備註 |
|---|---|---|
| 財報意外 | yfinance `earnings_dates` | 沿用舊碼演算法（`analyze_earnings_surprise`），僅移植邏輯不搬檔案 |
| 基本面 | yfinance `info`（PE、營業利益率、營收成長、負債權益比） | 同上（`analyze_fundamentals`）；ETF 已知欄位錯誤（費用率恆 0、PE 數量級錯）一律標記為不可靠，不當作 0 分計入 |
| 動能 | RSI、52 週位置走 yfinance `history(1y)`；**量能比（5 日/60 日）走內部 `daily_close.volume`**（[#15](https://github.com/NTUyu016/stock-analytic-platform/issues/15) 已擴充為日 OHLCV，來源 FinMind） | 同上（`analyze_momentum`），但量能比子指標**不可走 yfinance**——台股成交量實測 22.3% 交易日誤差 ≥100 倍（[`data-model.md`](./data-model.md) `daily_close` 表註記；[`docs/briefing/14-analysis-dimensions.md`](../briefing/14-analysis-dimensions.md) 附錄 C.1）。「六十日均量」一律指**最近 60 筆 `daily_close` 列**，非 60 個日曆交易日（停牌缺列時兩種讀法差 7 天以上，同上） |
| 分析師評等 | yfinance `info`（`recommendationKey`、`targetMeanPrice`、`numberOfAnalystOpinions`） | 同上（`analyze_analyst_sentiment`） |
| 大盤環境 | 內部 `benchmark_series` 表（[#16](https://github.com/NTUyu016/stock-analytic-platform/issues/16) 已建，發行量加權股價報酬指數含息，官方授權明確、已有完整歷史） | **不打外部 API**，是本地資料庫查詢；取代舊碼的 VIX／SPY／QQQ／GLD／TLT／UUP 六個美股宏觀指標 |
| 產業比較 | TWSE OpenAPI `https://openapi.twse.com.tw/v1/exchangeReport/MI_INDEX`（37 檔產業類指數），**每日存一次快照，不追溯歷史** | 取代舊碼的 12 檔 SPDR 類股 ETF；歷史查詢端點 `www.twse.com.tw/rwd/...` 落在另一張研究票（[#3](https://github.com/NTUyu016/stock-analytic-platform/issues/3)）判定的禁爬條款範圍，故不使用，改成每天存一筆自己累積 |

**放棄的兩維**：歷史財報型態（舊碼第四維，投入產出比不明確）、市場情緒（舊碼第八維，五個子指標裡多數對台股個股無等價資料，且權重僅 0.10，重建成本與效益不成比例）。

### 為什麼不是極簡、不是完整八維、不是台股本位重新設計

- 使用者已明確要求「每一維都要能對使用者解釋」（issue #14 留言）。完整移植八維會把台股沒有對等資料的子指標（如個股 put/call ratio）一起搬進來，變成解釋不出來的黑盒。
- 台股本位重新設計（主打月營收、三大法人、殖利率）最貼近「台股特色」，但需要一個每日盤後排程執行環境，而「排程要跑在哪台機器」是 [#17](https://github.com/NTUyu016/stock-analytic-platform/issues/17)（部署）尚未定案的題目——選這條路等於現在就押注一個還不存在的能力。
- 極簡（3–4 維，只吃 yfinance）完全放棄台股特色，對一個「台股為主」的平台不合理。
- 六維是唯一「有基本台股特色、但不依賴任何還沒拍板的東西」的組合：大盤環境與產業比較都改成查自己已有或即將自建的內部資料，不需要新的外部法遵風險，也不需要 #17 才能決定的排程能力。

### `lxml` 相依必須顯式宣告

舊碼的 `lxml` 是經由市場情緒維度的 `edgartools` 相依間接帶入的。v1 不做市場情緒維度，若照舊碼相依清單直接複製，`lxml` 會消失，而財報意外（維度一）與基本面（維度二）用到的 `stock.earnings_dates` 在缺少 `lxml` 時會被舊碼 `except Exception` 吞掉、靜默回傳 `None`——分數照樣算得出來、照樣給評等，沒有任何錯誤訊息。**實作時 `lxml` 必須顯式列進相依清單**，不得依賴它經由其他套件傳遞進來。

## 1. 美股與 crypto 分析頁（待決事項 4）

### 決定

**v1 不做**。持股表照樣顯示美股／crypto 標的的價格，但點進去沒有分析結論（明確的空狀態，不是報錯）。

### 為什麼

使用者目前的實際持股裡沒有美股標的，也沒有 crypto——不管選「兩套完整維度」「共用簡化維度」還是「通用框架先建起來」，都是在為不存在的資料先設計架構。等真的持有美股或 crypto 時再開新票決定，不會因為現在沒做而以後要拆掉重寫，只要六維的邏輯設計時不把資料結構寫死綁死在台股專屬格式上即可。

crypto 的決定是從美股這題類推得出的（同樣沒有對應持股、同樣的「不為不存在的資料先設計」理由），**使用者未針對 crypto 逐字拍板**，只是同一個原則的延伸適用——若日後認為 crypto 情況不同，應在該題重新確認。

## 2. 資料不足時的處理原則（待決事項 3 的隱藏前置）

### 決定

**資料不夠就明說不給結論，不硬湊。** 若一檔標的可用的維度數低於某個門檻（實作時定），畫面明確顯示「這支標的缺什麼資料、不給整體結論」，而不是像舊碼那樣只要 ≥2 維就照樣輸出一個 `buy`/`hold`/`sell`。

### 為什麼

這個專案已經在好幾張票撞過同一個教訓（#19 對帳只比股數、#10 的 `user_id`、#4 的 put/call 死碼）：**看起來正常、其實是錯的，比明顯異常更危險。** 一檔 ETF 只靠兩三個維度湊出的結論，畫面上會跟資料齊全的個股長得一模一樣，使用者看不出差別。與其給一個煞有其事的結論，不如老實告知資料不夠。

## 3. 評分與呈現（待決事項 3 殘留子問題）

待決事項 3 的核心（保留明確結論、採五級、必須同時呈現依據）已由使用者在 issue #14 留言定調，非本文重新決策的範圍。以下是定調之後仍未決的三個子問題：

### 3.1 信心度 → 廢除，改用 Coverage（維度覆蓋率）

舊碼的 `confidence` 其實就是 `final_score` 的絕對值（`confidence = abs(final_score)`），跟評等是同一個數字重複呈現兩次。v1 改用 **Coverage**（見 [`CONTEXT.md`](../../CONTEXT.md)）取代——「這個結論用了幾個維度、滿分幾維」——既然 §2 已經決定「資料不夠就明說不給結論」，會顯示結論的案例本來就已經通過最低門檻，此時「用了幾維」比一個跟評等重複的數字更有意義，也更貼合「不要黑盒」的要求。

### 3.2 評等被調節器下修時 → 標註原因

舊碼的調節器（近 52 週高、risk-off、地緣風險）只改 `recommendation`、不改 `final_score`，且降級理由只出現在自由文字 `caveats` 裡，沒有結構化記錄。v1 要求：**評等旁邊必須標一行下修原因**（如「已因近 52 週高下修」），不是只改數字不說明，也不必像同時顯示原始與調整後評等那樣把畫面複雜化。

### 3.3 本站評等 vs 分析師共識 → 用不同措辭

yfinance 的 `recommendationKey`（分析師共識）字面上與使用者選定的五級標籤完全相同（`strong_buy`/`buy`/`hold`/`sell`/`strong_sell`），畫面上會出現兩個 "Strong Buy"，一個是本站算的、一個是外部分析師的，而分析師共識本身還是本站評等的輸入之一。v1 用不同措辭區分：**本站結論用中文五級固定為「大幅偏多／偏多／中性／偏空／大幅偏空」，分析師共識維持原文英文**。不把分析師共識移出總分（那會動到已定案的六維權重結構），也不用版面隔離（成本更高、效果不確定）。

### 3.4 門檻切點做成設定值

五級需要四個切點，而 v1 沒有回測能力、沒有歷史分數分布可校準，四個切點目前唯一的依據是主觀判斷。比照 [#6](https://github.com/NTUyu016/stock-analytic-platform/issues/6)「費率一律不得硬編碼」的同型理由：**四個切點寫成可調設定值，不寫死常數**。這件事本身不是問題（v1 自用），但改動成本不該等到要調整時才發現是常數。

## 4. 運算時機與快取（待決事項 5）

### 決定

**A. 每次開頁即時算，v1 不落地快取。**

### 為什麼

六維定案後（§0），實際要打的外部資料源從舊碼測到的近 20 次呼叫（含市場情緒維度五個並行呼叫、類股 ETF 歷史）降到約 5 次（幾乎都是 yfinance 個股專屬呼叫：財報意外、基本面、動能的 RSI／52 週位置、分析師評等）；大盤環境、產業比較、動能的量能比子指標三者改查內部資料庫，幾乎不花時間。即時算的代價因此應該遠比 [`docs/briefing/14-analysis-dimensions.md`](../briefing/14-analysis-dimensions.md) §5.1(a) 測到的 25.3 秒輕（實際數字待實作後實測）。`api` 走 scale-to-zero（[`realtime-quotes.md`](./realtime-quotes.md) §3），行程內快取近乎無效，落地快取表又會撞上 [`data-model.md`](./data-model.md) 對 `portfolio_snapshot` 否決時的同一組理由（除非明確標成快取且可一鍵重算）——現階段沒有足夠證據支持先蓋一張表。

### 為未來鋪路，但不是現在的決定

使用者明確表示「先照 A 走，但未來會要往（存起來）走」。**計算函式的輸出格式從第一天就要讓每一維各自帶 `as_of` 時間戳**（不是只有一個籠統的整包時間），這樣之後若要加落地快取、甚至「部分維度盤後預算、部分維度開頁即時算」的混合做法，資料格式不需要改。這是唯一現在就要鎖定的部分；快取表本身、失效規則，都留到真的需要時再決定。

### 資料保存與運算時機是兩件事

「產業比較」需要的每日快照動作（§0）獨立於本節決定之外——那是資料保存（官方 API 只給最新一期，今天不存明天就沒有），不是分析結果快取，不管本節選哪個選項都要做。

## 5. 呈現形式（待決事項 6）

### 決定

**分數卡列表**：每一維一列，欄位為名稱、數值、分數、佔最終結論的貢獻。套用 [`dashboard-ui.md`](./dashboard-ui.md) 已定案的列表版面語彙（同一種列結構、`tabular-nums` 右對齊），不另外設計新的視覺語言。

### 為什麼不是雷達圖或貢獻度長條圖

- 本站顏色規則是硬約束：紅綠只給股價方向用，分數卡與雷達圖都不能用紅綠表示好壞，只能靠標籤。雷達圖額外有兩個問題：某一維缺資料時圖形會塌成 0，跟「這維分數真的是 0」在視覺上無法分辨（§2 剛好要防的情境）；八軸（現六軸）排列順序會不會影響觀感，本專案沒有驗證過。
- 貢獻度長條圖最貼合「不要黑盒」，但正負值同樣不能用紅綠，只能靠位置與標籤，設計成本比分數卡列表高，且沒有證據顯示分數卡列表不夠用。
- 使用者過去對「太分散又資訊不清楚」的評語（[`dashboard-ui.md`](./dashboard-ui.md) §1），解法是「面板改少改大」，不是新增更多小卡——分數卡列表沿用既有列表樣式，不引入新的版面單位。

### 不另開原型票

[#11](https://github.com/NTUyu016/stock-analytic-platform/issues/11) 當初為了整個網站的版面語言跑了五輪原型，但本題只是套用該票已經定案的列表樣式，風險遠低於當初的處境，不需要重複走一次原型流程。如果做出來後實際體驗不好，之後想加雷達圖當作分數卡列表的補充（不是取代），屆時再議。

## 6. 免責聲明與資料來源顯名

**頁尾一行**，與政府開放資料的顯名標示義務（[#3](https://github.com/NTUyu016/stock-analytic-platform/issues/3) §9：未盡標示義務「視為自始未取得授權」）合併成同一段文字。不放在結論旁邊（會讓畫面變吵，跟簡潔版面風格衝突），不用彈窗（使用者通常直接關掉不會看）。

## 7. 已知並接受的風險：yfinance 個人使用條款

Yahoo 財經資料條款寫明「僅限個人非商業使用」，而財報意外、分析師評等這兩維目前查到唯一的免費資料來源是 yfinance，沒有替代。本站雖然架在公開網際網路上，但 [#10](https://github.com/NTUyu016/stock-analytic-platform/issues/10) 已定：要登入、且只有手動加進白名單的帳號才能用——實際用得到資料的人只有使用者本人與受邀者，不是任何人都能白嫖。

**這是使用者親自做的法律風險判斷（issue #14 grilling，2026-08-08），不是技術判斷**，本文不代為背書其法律有效性。若使用者日後想開放給白名單以外的人使用，或有人提出異議，需要重新評估。
