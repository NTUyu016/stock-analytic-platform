## 1. 快照 vs 重算：重算，且不做快取

### 1.1 決定

**每日總資產曲線一律從 `transaction` + `daily_close` + `exchange_rate` 當場重算。不建 `portfolio_snapshot` 表，v1 也不做任何持久化快取。**

這維持 [`data-model.md`](./data-model.md) 的核心原則 1（Transaction 是唯一事實來源），並落實它「刻意不做的表」一節對 `portfolio_snapshot` 的既有立場。

### 1.2 為什麼快照在本專案是錯的答案

[#19](https://github.com/NTUyu016/stock-analytic-platform/issues/19) 定案時交出了一個判準：**輸入越不規律，就越不能用純快照**。而實測結果是「不規律」，且不規律的來源是結構性的，不是紀律問題：

| 來源 | 為什麼無法預測 |
|---|---|
| 國泰對帳單匯出**分頁截斷**（樣本 59 筆只給 50 筆） | 補匯的時機取決於使用者哪天發現 |
| 股利與除權息**永遠是事後補登** | 對帳單裡根本沒有這類列，而它們會改變股數與成本基礎 |
| 標的反查失敗**中斷整批匯入**（#19 選了原子性） | 一次匯入可能整批延後數天 |

三者指向同一件事：**任意一段歷史區間的交易集合，隨時可能因為補登而改變**。

而快照的失效方式正是本專案最忌諱的那種：

> 補登一筆三個月前的交易後，快照表裡那三個月的每一列都變成錯的。**沒有任何錯誤訊息**，曲線照畫，數字照顯示，只是全錯。

### 1.3 為什麼「重算太慢」這個顧慮不成立

[`dashboard-ui.md`](./dashboard-ui.md) §7 曾提出一個顧慮：資產走勢要能拖曳選取任意區間，「每日總資產必須逐日可得，且查詢必須夠快以支撐 60fps 的拖曳」，並據此判斷「快照 vs 重算的成本差距遠大於原先估計」。

**這個判斷可以撤回，理由有兩層：**

**第一層：拖曳根本不打後端。** 拖曳選取操作的是**瀏覽器裡已經載入的那條序列**。後端只需要在切換期間（1M / 3M / 6M / 1Y / 全部）時回一次完整序列——1 年約 244 個點，JSON 量級是個位數 KB。60fps 是前端的事，與資料庫無關。

**第二層：資料量本來就很小。** 實測數字見 §1.5。

### 1.4 若日後真的需要快取

只有在**同時滿足**以下兩條時才加，且加的是快取不是事實來源：

1. 標的數 × 歷史年數使 `daily_close` 超過百萬列量級
2. 已實測確認查詢時間是使用者可感知的瓶頸（而非猜測）

且必須符合 [#19](https://github.com/NTUyu016/stock-analytic-platform/issues/19) 留下的約束：**補登時要能精準失效受影響的區間**——從最早受影響的 `traded_on` 往後全部作廢，而不是「刷新最近 N 天」。

> ⚠️ **「刷新最近 N 天」是這裡最危險的偷懶做法**：它對 99% 的情況有效，對「補登三個月前的交易」無效，而那正是本專案已知會固定發生的情況。

### 1.5 實測

> 本節數字待原型結果填入。

## 2. 粒度：每日一點，不留盤中

**歷史只留日線。** 盤中報價依 [`data-model.md`](./data-model.md) 核心原則 3 不落地，因此歷史曲線的每一點都是**收盤價**。

- **今天這一點**：盤中時取當前 Quote，收盤後由盤後排程寫入 `daily_close` 後才固定下來。故**今天的點在盤中會跳動，隔天才凍結**——這是正確行為，UI 應以「今日」標示而非畫成已定案的歷史點。
- **曲線起點**：使用者最早一筆 `transaction.traded_on`。不是固定年數。
- **期間選項**：1M / 3M / 6M / 1Y / 全部（[`dashboard-ui.md`](./dashboard-ui.md) §7 原列到 1Y，本文補上「全部」）。

`daily_close` 的回補範圍、來源與硬性規則已由 [#15](https://github.com/NTUyu016/stock-analytic-platform/issues/15) 鎖定，本文**完全沿用、不放寬**：走 FinMind `TaiwanStockPrice`、回補到每檔建倉日、停止買賣日不補列。詳見 [`alerts.md`](./alerts.md) §2.4。

### 2.1 回補是一次性批次，不是問題

[#16](https://github.com/NTUyu016/stock-analytic-platform/issues/16) 原列的待決事項「新增一支從未持有過的標的時，歷史價從哪來、回補多久」在本專案的規模下不構成成本：

- FinMind **一次請求即回該檔全歷史**（[實測](../research/tw-volume-anomaly-and-history.md)：2330 單次回 8,052 列）
- 免費層 **300 req/hr（不帶 token）／600 req/hr（帶 token）**
- 因此**新增一檔標的 = 一次請求**，回補到建倉日只是把回應裁掉前段

**真正需要注意的是觸發時機**：回補必須發生在**匯入交易的當下**（而非等隔天的盤後排程），否則使用者匯入完一批歷史交易後打開績效頁，會看到一條起點錯誤的曲線——**沒有錯誤訊息，只是曲線比實際短**。

**v1 沒有 watchlist**，因此不存在「從未持有卻要回補」的情況；回補的觸發點只有一個，就是某檔標的第一次出現在 `transaction` 裡。

## 3. 股利：雙軌，且明確分軌

### 3.1 決定

**現金股利不沖減成本基礎。** 成本均價永遠是實際買進的加權平均，與券商庫存均價一致。股利獨立累計為**股利收益**。

這**修訂了 [#9](https://github.com/NTUyu016/stock-analytic-platform/issues/9)**：[`data-model.md`](./data-model.md) 原記「`CASH_DIVIDEND`：只有 `cash_amount`，不改股數，**降低成本基礎**」，本文改為不改成本基礎。

### 3.2 為什麼

[`../research/tw-trading-costs-taxes.md`](../research/tw-trading-costs-taxes.md) §4.2 已識別出台股實務上存在兩套並行慣例：

| | 軌 A（帳面／對帳用） | 軌 B（績效／還原用） |
|---|---|---|
| 現金股利 | 不沖減成本 | 計入總報酬 |
| 用途 | 與券商庫存均價一致 | 報酬率、含息年化 |

而該文同時給出**兩軌的接合恆等式**，本專案將它列為硬性不變量：

> **軌 A 的價差損益 ＋ 股利淨額 ＝ 軌 B 的總損益**

本文的選擇是：**帳面走軌 A，績效走軌 B，兩者在同一個畫面上都出現，但永遠分開標示。**

### 3.3 沖減成本的那條路為什麼被否決

除了對不上券商之外，它有一個會**靜默翻轉正負號**的失效模式：

長期持有高殖利率標的時，累計股利可以超過原始成本，使成本基礎降到零以下。而報酬率是 `(市值 − 成本) / 成本`——**分母一旦為負，報酬率的正負號整個翻過來**。一支大賺的股票會顯示成大賠，且不會有任何錯誤訊息。

這與 [#15](https://github.com/NTUyu016/stock-analytic-platform/issues/15) 拒絕 `CHECK` 保護 `jsonb`、[#19](https://github.com/NTUyu016/stock-analytic-platform/issues/19) 拒絕 `transaction.status` 是同一個形狀：**不是「比較難用」，是「錯了不會叫」**。

### 3.4 股票股利

**維持 [#9](https://github.com/NTUyu016/stock-analytic-platform/issues/9) 既有規則不變**：總成本不變、總股數增加 → 均價被稀釋。兩軌對股票股利的處理一致，無分歧。

### 3.5 股利的「淨額」是哪個數字

績效一律用**實收淨額**，不是宣告總額。台灣居住者的股利本身**免予扣繳所得稅**（僅非居住者 21%），但仍有兩項會在配息當下被扣掉：

| 扣項 | 規則 | 來源 |
|---|---|---|
| 二代健保補充保費 | 單次給付達 **20,000 元**起扣，**達門檻即以全額計** 2.11%；單次上限 1,000 萬元 | 全民健保法 §31、扣取及繳納辦法 §4 |
| 美股股利就源扣繳 | **30%**（台美無所得稅協定） | IRC §871 / IRS Pub. 515 |

**欄位對應（不需改綱要）**：沿用 [`data-model.md`](./data-model.md) 既有的「各類型欄位語意」慣例——

- `cash_amount` = 股利**總額**（宣告金額）
- `tax` = 該筆股利被扣掉的稅費合計（補充保費／就源扣繳）
- **實收淨額 = `cash_amount` − `tax`**

> ⚠️ **把總額當成現金流會讓 XIRR 系統性高估。** 美股 30% 的扣繳尤其明顯。這條必須有測試涵蓋。

> 註：`tax` 欄在 `BUY` / `SELL` 是證交稅，在 `CASH_DIVIDEND` 是補充保費／扣繳。**同一欄在不同 `type` 下語意不同**，這沿用綱要既有做法（`quantity`、`cash_amount` 本來就如此），但必須寫在欄位註解裡，否則日後會有人問「為什麼股利有證交稅」。

### 3.6 所得稅不進系統

合併計稅 vs 分開計稅（臨界邊際稅率 36.5%）是**年度申報**的事，發生在系統之外、且是全戶合併判斷。**v1 不計算所得稅，績效數字為稅前（不含綜所稅）但已扣除配息當下的扣繳與補充保費。** 這個界線必須在 UI 上寫明，否則使用者會以為那是稅後報酬。

## 4. 報酬率：四個指標，各有其位

**通則（沿用 [#16](https://github.com/NTUyu016/stock-analytic-platform/issues/16) 前置討論的結論，列為硬性規則）：**

> **絕對金額不會騙人，百分比會。** 任何百分比旁邊都必須有對應的絕對金額，且絕對金額的字級不得小於百分比。

| 指標 | 回答什麼 | 用在哪 |
|---|---|---|
| 簡單報酬率 | 這個部位現在是賺是賠 | 持股表每列（§4.1） |
| 全期總報酬 | 我從頭到現在總共賺了多少 | 首頁主數字（§4.2） |
| XIRR | 我的錢實際年化賺幾 % | 首頁次要數字（§5） |
| TWR | 我的選股比大盤好嗎 | 大盤比較圖（§6） |

### 4.1 持股表每列：簡單報酬率，不含股利

`(市值 − 成本總額) / 成本總額`。**不含股利**，因此與券商 App 顯示的數字對得上。

**含股利的版本放在展開處**，不放在列上。理由：同一張表出現兩個都叫「報酬率」的欄位，是製造誤讀的最短路徑。

> 這**修訂了 [`dashboard-ui.md`](./dashboard-ui.md) §5** 的欄位定義：該表的「報酬率」欄需明確標示為不含股利，展開列補上「含股利總報酬」與「已領股利」兩個絕對金額。

### 4.2 首頁總報酬：涵蓋全部歷史

**分子分母都必須涵蓋已出場的部位。**

```
總報酬（絕對金額）＝ 已實現價差損益 ＋ 股利淨額 ＋ 未實現損益
簡單報酬率        ＝ 總報酬 / 累計投入本金
```

其中「累計投入本金」= 所有 `BUY` 的交割金額合計（含費用），**不扣掉已賣出的部分**。

**為什麼必須涵蓋已出場部位**：只算當前持股會讓賠錢停損出場的部位從分母消失，而賺錢的還在手上——**倖存者偏差在自己的帳戶裡重演**。年度回顧只會看到還在手上的贏家。

呈現形式（[`dashboard-ui.md`](./dashboard-ui.md) §1 的「總資產」面板）：

```
總報酬   +247,230              ← 絕對金額，字級最大
         +15.4% · 年化 +9.2%   ← 兩個百分比並列，次要層級
         大盤同期 +11.8% · 年化 +7.1%
```

## 5. XIRR

### 5.1 做，但必須附現金流明細

首頁的「年化」數字採 **XIRR（金額加權內部報酬率）**。

**代價必須被正視**：XIRR 沒有解析解，只能用迭代求根。使用者**無法用計算機驗算**。在一個自用、自建的系統上，「使用者無法驗證的數字」是真實的信任成本。

**強制配套**：提供 XIRR 所用**現金流明細的展開檢視**——哪天流入多少、哪天流出多少、期末市值多少。使用者至少能驗證輸入正確，即使無法驗證求根過程。**這不是加分項，是這個數字得以出現在畫面上的前提。**

### 5.2 現金流的定義

| Transaction Type | 現金流 | 符號 |
|---|---|---|
| `BUY` | 交割金額（`quantity × price + fee + tax`） | **負**（流出） |
| `SELL` | 淨收金額（`quantity × price − fee − tax`） | **正**（流入） |
| `CASH_DIVIDEND` | 實收淨額（`cash_amount − tax`，見 §3.5） | **正** |
| `STOCK_DIVIDEND` | **0**（無現金往來） | — |
| `ADJUSTMENT` | 依 `cash_amount` 正負 | 依實際 |
| 期末 | **今日總市值** | **正** |

**幣別**：所有現金流**先用當日匯率換算成 TWD 再求解**。

> ⚠️ **把不同幣別的現金流直接丟進同一次 XIRR 是錯的，而且不會報錯**——它會安靜地把美元當台幣加總。這條需要契約測試。

### 5.3 求根的數值防護

> 本節待原型結果填入。

### 5.4 交割帳戶現金流：不需要

[#19](https://github.com/NTUyu016/stock-analytic-platform/issues/19) §13 把「交割帳戶現金流未被追蹤」列為待補，並註明「若績效要做 XIRR 或現金報酬率，需要它」。

**本文的結論是 v1 不需要，理由是定義問題不是省略：**

XIRR 衡量的是「**投入到標的裡的錢**」的報酬率。閒置在交割帳戶裡的現金**不是投資組合的一部分**——它沒有被投資，也不該被計入報酬的分母。把它加進來，衡量的就變成另一個問題（「我的全部資金配置效率如何」），那是現金管理，不是選股績效。

因此 §5.2 的現金流表已經完備：每一筆買賣與股利本身就是「錢進出投資組合」的完整紀錄，不需要知道交割帳戶餘額。

> **這關掉了 #19 §13 對 v1 的疑問。** 若日後要做「含閒置現金的整體資金報酬率」，那是一個**新的、不同的**指標，屆時才需要交割帳戶餘額——而不是現在這個指標缺了東西。

## 6. 大盤比較：TWR

### 6.1 為什麼比較用 TWR 而不是 XIRR

大盤沒有資金進出。拿一個含資金進出的指標（XIRR）去比一個沒有資金進出的對象，比較本身就不成立——**加碼的時點會被算進你的成績，而指數沒有時點可言**。

TWR 把各期漲跌相乘、**排除資金進出的影響**，衡量的是「每一塊錢在裡面待著的期間表現如何」，這才與指數同構。

### 6.2 日 TWR 的計算與那個會毀掉整條曲線的錯

逐日鏈式相乘：

```
r_t = (V_t − F_t) / V_{t−1} − 1
TWR(a→b) = Π(1 + r_t) − 1
```

- `V_t` = 第 t 日收盤的總資產（TWD）
- `F_t` = 第 t 日的**淨外部現金流**（買進為正、賣出與股利為負）

**現金流時點採「日終」假設**：`V_t` 是收盤市值，當日買進的部位已含在其中，減去 `F_t` 即移除注入的本金，比值只反映價格變動。代價是「當日買進到收盤之間的漲跌」不被計入，誤差上限為 `新投入金額 × 當日盤中漲跌幅`。日粒度下這是無法消除的，只能明確選定並全程一致。

> ⚠️ **忘記減 `F_t` 會讓整條 TWR 曲線報廢，而且不會報錯。**
>
> 合成範例：某日總資產 150,000，當天加碼 900,000，收盤總資產 1,050,000。
> - 正確：`r = (1,050,000 − 900,000) / 150,000 − 1 = 0%`
> - 忘記減：`r = 1,050,000 / 150,000 − 1 = +600%`
>
> 那一天的 +600% 會被乘進整條鏈，之後每一天的累計報酬都是錯的。曲線依然平滑、依然單調、依然看起來很合理。**這是本文優先級最高的一條測試。**

**邊界規則（`V_{t−1} = 0`）**：首日、或清倉後重新建倉的那一天，前一日市值為零，比值無定義。

> **規則：`V_{t−1} = 0` 的日子不產生報酬率，TWR 鏈從下一個 `V > 0` 的日子重新接續。**
>
> 不可接 0%（會在圖上畫出一段假的持平），也不可中斷曲線（清倉一年後重新進場是正常行為，不該讓歷史績效消失）。

### 6.4 多幣別部位讓比較本身失真，必須寫在畫面上

總資產曲線與 TWR 都以 TWD 計算（每日用當日匯率換算），所以**外幣部位的匯率損益會被算進「你的績效」**——而台股基準指數完全沒有匯率成分。

這不是計算錯誤，是**兩個序列本來就不完全可比**。可能的做法有三種：

| 做法 | 問題 |
|---|---|
| 假裝沒事，直接比 | 美元走強的年份會讓你以為自己選股變厲害了 |
| 把匯率貢獻拆出來單獨顯示 | 正確，但需要多一組分解邏輯與多一張圖 |
| **在圖上註明「含匯率影響」** | v1 採用 |

**v1 採第三種**：當使用者持有任何非 TWD 計價的部位時，大盤比較圖必須顯示「本曲線含匯率影響，基準不含」的註記。這是最小的誠實成本。

> **實作上的陷阱**：使用者目前**沒有任何美股部位**，因此整條匯率路徑在 v1 上線時是**沒有真實資料走過的**。
> 這意味著它會是「寫了但沒被驗證過」的程式碼——第一次買進美股的那天才會第一次執行，而那天正好是最不想除錯的時候。
> **對策**：`exchange_rate` 的換算路徑必須有以**合成資料**驅動的測試，涵蓋「當日無匯率列（假日）」與「跨幣別加總」兩條，且列入 [`tech-stack.md`](./tech-stack.md) §7 的分層測試策略中「錢的計算」那一層。

## 7. 圖表

### 7.1 總資產曲線

[`dashboard-ui.md`](./dashboard-ui.md) §7 已定義互動（拖曳選取區間、區間外壓淡至 32%、Esc 取消）。本文只補資料面：曲線值為**每日收盤總資產（TWD）**，起點為最早交易日。

### 7.2 大盤比較曲線

你的 TWR 累計 與 基準指數累計，**同時正規化到起點 = 100**。兩條線疊在同一張圖。

> ⚠️ **不可把「總資產絕對金額」與「指數點數」畫在同一張圖上**，即使用雙 Y 軸——雙 Y 軸可以透過縮放讓任何兩條線看起來想交叉幾次就交叉幾次。正規化到同一起點是唯一誠實的畫法。

### 7.3 個股貢獻度

**絕對金額（TWD）的橫條圖，含已出場標的**，依貢獻度排序。

```
每檔貢獻度 = 該檔已實現價差損益 ＋ 股利淨額 ＋ 未實現損益
```

**不變量：所有標的的貢獻度合計 = §4.2 的總報酬。** 這是一個可自動驗證的等式，應寫成測試。

> ⚠️ **貢獻度不可用百分比呈現。** 各檔的報酬率分母不同，加總沒有意義——把它們排在一起會讓人以為可以相加。這是「絕對金額不會騙人」在圖表上的直接應用。

### 7.4 月／年報酬長條圖

**主軸為絕對損益（TWD）**，每根長條 = `V_期末 − V_期初 − F_期間`。次要標註該期 TWR%。

紅漲綠跌，遵守 [`dashboard-ui.md`](./dashboard-ui.md) §2——**這是介面上少數幾個允許出現顏色的地方之一**，因為它表達的正是價格方向。

### 7.5 資產配置隨時間變化

堆疊面積圖，每一層為某標的的每日市值（TWD）。資料與 §7.1 同源，只是不加總。

**標的數多時的處理**：超過 8 檔時，市值最小的合併為「其他」。理由與 [`dashboard-ui.md`](./dashboard-ui.md) §2 一致——類別色在淺色模式對比不足，**每一層都必須有可見的直接標籤**，而超過 8 層就標不下了。
