## 1.2 實測結果（本票要求的實算）

### （a）基準情境：10 標的 × 10 年 × 1,500 筆交易

| 查詢 | p50 | p95 | 說明 |
|---|---:|---:|---|
| **A. 任意單一日總資產（純重算）** | **0.70 ms** | 1.32 ms | `SUM(signed qty) WHERE traded_on <= D` → LATERAL 取各標的當日（或前一個有值日）收盤價 → 乘匯率 |
| B. 全期間 10 年曲線（**天真版**，每支標的只在自己有收盤價的日子計入） | 39.4 ms | 54.3 ms | 2,514 個點。**此版本在跨市場日曆不一致時會算錯**（見 1.4 R2） |
| C. 全期間 10 年曲線（**LOCF 正確版**，統一日曆 + 價格與匯率前值補齊）| 306 ms | 326 ms | 同 2,514 點，數字才是對的 |
| **C'. 同上，查詢調優後**（限「曾持有」標的、以第一筆交易日起算格子、聚合用 `float8` 而非 `numeric`） | **97 ms** | 100 ms | **與 C 完全同義，只是寫法不同 → 3.2 倍差距純粹來自 SQL 寫法** |
| G. SQL 只撈原始列（25,002 + 1,500 列）+ 曲線在應用層算 | 撈列 39 ms + 算 12 ms = **51 ms** | — | 純 Python 迴圈，未用 NumPy |
| D. 近 1 年曲線（252 點，LOCF） | 14.7 ms | 16.1 ms | |
| E. 近 3 個月曲線（66 點，LOCF） | 9.3 ms | 9.8 ms | |
| **F.【對照】從已物化的快取表讀同一條全期間曲線** | **3.8 ms** | 4.6 ms | 這就是「有快照表」能買到的東西 |

**→ 基準情境下「重算 vs 快取」的實際差距是 51–97 ms 對 3.8 ms，約 13–25 倍比值，但絕對值差距是 ~50–90 ms。**

### （b）放大情境（看未來會不會撞牆）

| 情境 | 單日重算 | 全期間曲線（調優 SQL） | 全期間曲線（撈列 + 應用層算） | 快取表讀取 |
|---|---:|---:|---:|---:|
| 10 標的 × 10 年（1,500 筆） | 0.70 ms | 97 ms | 51 ms | 3.8 ms |
| 50 標的 × 10 年（2,504 筆，125k 列） | 1.42 ms | — | — | 3.2 ms |
| 50 標的 × 20 年（5,021 筆，250k 列 / 22 MB） | 2.05 ms | 1,175 ms | 459 ms | 6.3 ms |

**單日重算幾乎不隨規模成長**（0.70 → 2.05 ms，資料量 10 倍）。**整條曲線則接近線性成長**，因為它要碰每一列 `daily_close`。

### （c）成本基礎的序列遞迴，成本比想像低得多

移動加權平均成本基礎**不是**單純的累加，賣出時要 `cost -= qty × avg_before`，是有順序相依的遞迴（`tw-trading-costs-taxes.md` §5.3 的公式）。這在 SQL 裡很難用視窗函式表達，直覺上會以為它昂貴。實測：

> **5,021 筆交易跑完整套移動加權平均 + 已實現損益累計＝ 5.09 ms／次**（純 Python 迴圈，100 次平均）。1,500 筆約 1.5 ms。

**關鍵性質：這個成本只與交易筆數有關，與天數、與標的數無關。** 而 [#19](https://github.com/NTUyu016/stock-analytic-platform/issues/19) 已把交易量釘在 150 筆／年。

**因此「重算成本」拆得開來看是兩件不同的事：**

| 成分 | 隨什麼成長 | 基準情境成本 |
|---|---|---|
| 逐日總市值（累計股數 × 收盤價 × 匯率） | **天數 × 標的數**（25,002 列） | 39–97 ms |
| 成本基礎與已實現損益（序列遞迴） | **交易筆數**（1,500 列） | ~1.5 ms |

貴的是前者，而前者是**簡單的累加 + 前值補齊**，不是遞迴。

### （d）60fps 拖曳到底對後端要求什麼——結論與 `dashboard-ui.md` §7 的推論方向相反

每影格預算 16.7 ms。實測：

| 做法 | 每影格成本 | 可行？ |
|---|---:|---|
| 每影格打一次後端算區間報酬 | DB 端 0.70 ms + **HTTP RTT**（本機外必然 > 10 ms，且 `api` 走 scale-to-zero 可能冷啟動）| ❌ 架構上就不成立 |
| **一次抓整段曲線，之後在瀏覽器本地算** | **0.87 µs／次**（區間 TWR 為兩個累積指數相除，O(1) 查表）| ✅ 預算的 **1/19,000** |
| 同上，但每影格重跑一次全期間 XIRR（1,501 筆現金流、牛頓法收斂） | **1.35 ms**（max 3.9 ms） | ✅ 仍在預算內 |

**Payload 實測（決定「一次抓整段」可不可行）：**

| 內容 | raw JSON | gzip |
|---|---:|---:|
| 總資產曲線，10 年 2,514 點，純數值陣列（日期用起點 + 索引隱含） | 24.6 KB | **9.8 KB** |
| 同上但每點是 `{d, v}` 物件 | 81.0 KB | 13.8 KB |
| **個股貢獻度**：10 支標的各一條市值曲線 × 2,514 天 | 215.5 KB | **81.7 KB** |
| 同上放大到 50 支 | 832.0 KB | 384.8 KB |

> **這是本票最重要的一個實算結果**：`dashboard-ui.md` §7 寫「查詢必須夠快以支撐 60fps 的拖曳……這使得快照 vs 每次重算的成本差距遠大於原先估計」。**實算顯示這條推論的方向是反的。** 拖曳互動需要的不是「快的查詢」，而是「**一次拿得到整段**」——而整段只有 9.8 KB（gzip）。一旦整段在前端手上，任何區間的絕對變化、百分比、TWR 都是 O(1) 陣列查表，連 XIRR 都在預算內。
>
> 換句話說，**拖曳互動幾乎不放大快照與重算的差距**；它把差距壓到「開頁那一次」。真正的問題退化成：**開頁載入時多等 50–95 ms 值不值得換一張快取表。**
>
> ⚠️ 但 §7 那條推論本身是 #11 的定案文字，若本票的結論與它衝突，**`dashboard-ui.md` §7 需要一併修訂**——那是 spec 對 spec 的修訂，不是新增。

## 1.3 選項盤點

### 選項 A：純重算，不建任何持久化中間物

每次要曲線就跑 SQL。

| | |
|---|---|
| **代價** | 開頁 51–97 ms（基準情境，本機下界）；正式環境可能 2–4 倍 → 100–400 ms。50 標的 × 20 年會到 0.5–1.2 秒 |
| **買到什麼** | `data-model.md` 核心原則 1 完全成立，零一致性風險，補登後歷史**立刻**就是對的（`transaction-input.md` §9 的「補登之後歷史就是對的」保證不需額外機制維護） |
| **風險** | 曲線 SQL 相當長（LOCF + 統一日曆 + 匯率補齊），是全系統最複雜的一段 SQL；**寫法差 3.2 倍**（306 ms vs 97 ms）代表它容易被寫慢又不自知 |
| **改綱要？** | **否**。`data-model.md` 一個字都不用改 |

### 選項 B：`portfolio_snapshot` 作為**快取表**（#16 留言與 `data-model.md` 都已預留這條路）

物化每日總資產，補登時從最早受影響的 `traded_on` 往後失效重建。

| | |
|---|---|
| **代價** | 讀取降到 3.8 ms（快 13–25 倍）；但要寫失效邏輯、要處理「快取有沒有算到最新一天」、要有「完全重建」的逃生指令 |
| **重建成本實測** | 全量重建 = 跑一次曲線查詢（51–97 ms）。**因為全量重建就這麼便宜，「精準區間失效」的增量邏輯在基準情境下是不必要的複雜度**——直接砍掉重建即可 |
| **風險（最重要的一條）** | 這張表**不會有任何錯誤訊息**告訴你它過期了。與 [#10](https://github.com/NTUyu016/stock-analytic-platform/issues/10) 的 `user_id`、[#19](https://github.com/NTUyu016/stock-analytic-platform/issues/19) 拒絕在 `transaction` 加 `status` 是**完全同一個形狀的風險**：漏了不會噴錯，只會靜默地給出舊數字。本專案已兩次以此理由否決設計 |
| **緩解** | 若採此路，可考慮的驗證機制：快取列存一個「輸入指紋」（該日以前的 `max(transaction.id)` + `count`），讀取時比對不合就重建。這讓「過期」變成可偵測而非靜默 |
| **改綱要？** | **✅ 會回頭修改 `data-model.md`**：需把 `portfolio_snapshot` 從「刻意不做的表」搬出來，並明確標記為快取（含 `user_id`、`trade_date`、`total_twd`、指紋欄位）。這是本票最可能產生的綱要連鎖影響 |

### 選項 C：不物化總資產，改物化「較低層的中間物」

例如物化一張 `daily_holding(instrument_id, trade_date, shares)`（逐日股數，價格照樣即時 join），或物化 LOCF 後的價格網格。

| | |
|---|---|
| **代價** | 比 B 小的失效面（股數只受 `transaction` 影響，不受 `daily_close` 回補影響），但省下的時間也少——實測 39 ms（天真版，含價格 join）已含價格運算，單純省掉累加不會省太多 |
| **風險** | 兩個表都要維護一致性，複雜度未必低於 B |
| **改綱要？** | **✅ 會**（新增一張表） |
| **未查證** | **未能查證**：本次 benchmark 沒有單獨量測「只物化股數」的收益，因為它需要拆開 LOCF 與累加兩段分別計時。若這個選項在 grilling 中被認真考慮，需要補跑 |

### 選項 D：前端持有整段，後端只提供「原始素材」

後端只回 `daily_close` 與 `transaction` 的原始列（實測撈 25,002 + 1,500 列 = 39 ms），曲線與所有指標都在瀏覽器算（12 ms）。

| | |
|---|---|
| **代價** | payload 從 9.8 KB 膨脹到把 25,002 列價格傳過去（未量測，粗估 raw 數百 KB／gzip 數十 KB）；曲線邏輯**在前後端各存在一份**（後端做 API 與匯出仍需要），這是明確的重複實作 |
| **買到什麼** | 後端 SQL 極簡；前端可做任何切法（個股貢獻度、資產配置變化）不用再打 API |
| **風險** | **金額計算在兩個語言各寫一次**，而 `tech-stack.md` §7 規定「錢的計算嚴格 TDD」——等於兩套測試。且 JS 沒有 `numeric`，浮點誤差與後端不會逐分位一致 |
| **改綱要？** | 否 |

### 選項 E：混合——曲線重算，但 `daily_close` 之外再快取「最新一日的部位」

只快取「今天」的 Position 與成本基礎（供首頁與持股表用），歷史曲線一律重算。

| | |
|---|---|
| **代價** | 首頁最熱的路徑受益；但實測**單日重算只要 0.70 ms**，快取它幾乎沒有收益 |
| **改綱要？** | ✅ 會（等於 `position` 表，`data-model.md` 明令不做） |

## 2.2 量級實算

| 粒度 | 每年列數（單一使用者總資產一條線） | 對照 |
|---|---:|---|
| 每日收盤 1 筆 | ~250 | 10 年 = 2,500 列 |
| 盤中每 5 分鐘（09:00–13:30 = 54 格） | ~13,500 | **1 年就超過 10 支標的 10 年份 `daily_close` 的一半** |

## 3.2 三個演算法在「中途加碼」時給什麼答案——具體數字

### 範例（合成數字，刻意做成三個指標會分岔的形狀）

```
2025-01-01   投入 100,000 買 A 股
2025-06-30   A 股市值漲到 150,000               ← 半年 +50%
2025-07-01   再投入 900,000 加碼 A 股           ← 此刻總投入 1,000,000、總市值 1,050,000
2025-12-31   A 股再漲 5%，年底總市值 1,102,500
```

年底時，同一個帳戶三種算法：

| 指標 | 算式 | 答案 | 它在回答什麼 |
|---|---|---:|---|
| **簡單報酬率** | `(1,102,500 − 1,000,000) / 1,000,000` | **+10.25%** | 「我投進去的每一塊錢，現在變成多少」 |
| **TWR（時間加權）** | 拆成兩段，各段自己的漲幅相乘：`(150,000/100,000) × (1,102,500/1,050,000) − 1` = `1.5 × 1.05 − 1` | **+57.5%** | 「如果每段期間我都只投 1 塊錢、不管我實際投多少，這個投資組合的表現如何」 |
| **XIRR（金額加權）** | 求 r 使 `−100,000/(1+r)^0 − 900,000/(1+r)^0.5 + 1,102,500/(1+r)^1 = 0` | **+19.34%**（年化，數值解） | 「我這筆錢的實際年化報酬率是多少」 |

> 三個數字均已實算驗證（`scratchpad` 內以二分法求根確認 XIRR = 19.3350%）。**同一個帳戶、同一天、同一筆錢，三個都「正確」的算法給出 +10.25% / +19.34% / +57.50%。**

### 三個答案為什麼差這麼多，以及各自誠實在哪

**TWR +57.5%：這是「標的表現」，不是「你賺了多少」。**
它刻意把「你投了多少錢」這件事整個抵銷掉，只留下「每一塊錢在每一段期間的成長倍數」。它給 +57.5%，是因為前半年漲 50% 那一段，**不管你當時只投了 10 萬還是投了 100 萬，權重都一樣**。

- **它誠實在**：你只投了 10 萬就抓到那波 50%，這件事在 TWR 眼裡確實是「選股能力」的展現。
- **它不誠實在**：你的錢實際上沒賺 57.5%——你只賺了 102,500 元。
- **為什麼用它跟大盤比才公平**：大盤指數沒有「加碼」這回事，它就是一段一段漲跌相乘。你的帳戶如果用會被加碼稀釋的指標去跟它比，就是拿兩把不同的尺量。這正是 issue #16 留言表格所指的用途。

**簡單報酬率 +10.25%：算術完全正確，但它沒有時間維度，而且會被加碼稀釋。**
issue #16 第 1 則留言已列出它的四個失效情境，本例正是失效 ②：6 月時是 +50%，7 月只因為「加碼」這個中性動作，數字就掉到 +5%（本例期末 +10.25%）。你沒做錯任何事，數字卻變難看。

- **它誠實在**：分子分母都是你能用計算機三秒驗算的真實數字。**這是它唯一但極重要的優點**。
- **它不誠實在**：把一個 8 年的 +15% 和一個 3 個月的 +15% 顯示成同一個東西。

**XIRR +19.34%：這是「你的錢的年化報酬率」，也是三者中唯一同時考慮金額與時間的。**
它的邏輯是：把每一筆「錢進去」與「錢出來」標上日期，去找一個年化利率 r，使得所有現金流用 r 折現後剛好等於 0。你在 7 月才投入的 90 萬只享受了半年的 5%，XIRR 會如實反映這一點——所以它遠低於 TWR 的 57.5%；但它同時知道「這 100 萬平均只放了約 0.55 年就賺了 10.25 萬」，所以又明顯高於簡單報酬率的 10.25%。

- **它誠實在**：如果你把這筆錢放定存，要放到 19.34% 年利率、且按同樣的時點存入，才能得到相同結果。這是最貼近「我到底賺了多少」的口徑。
- **它不誠實在**：沒有不誠實，但**你驗算不了**（F3-4）。牛頓法迭代出來的數字，你只能相信它。
- **另一個坑**：現金流全部同向（一路買不賣）時 XIRR 仍可解；但若期間內有大額進出且期末市值接近 0，牛頓法可能不收斂或收斂到荒謬解。這是實作必須處理的邊界，不是理論問題。

### 一句話對照

| | 分母是 | 加碼會影響它嗎 | 使用者能驗算嗎 |
|---|---|---|---|
| 簡單報酬率 | 目前總成本 | **會**（稀釋） | ✅ 三秒 |
| TWR | 無（各期相乘） | **不會**（刻意排除） | ⚠️ 要有每日曲線才驗得動 |
| XIRR | 每筆現金流各自的時間權重 | **會**（正確地反映） | ❌ 只能驗輸入不能驗輸出 |

### ⚠️ 失效 ③（已出場部位）在三者中的表現不同——這是本票要解的那一條

假設 2025 年你賣掉一支賠 5 萬的股票，另一支賺 10 萬的還握著：

| 指標 | 會不會漏掉那筆 −5 萬 |
|---|---|
| 簡單報酬率（依 `CONTEXT.md`，Position 是當前持有狀態）| **會漏**。分子分母都只有「還在手上的」 |
| TWR | **不會漏**——只要 TWR 是從**每日總資產曲線**推導的（賣出那天資產掉下來會留在曲線上） |
| XIRR | **不會漏**——賣出是一筆正現金流，本來就在現金流序列裡 |

> **這給出一條硬約束**：只要「總報酬」是從**每日總資產曲線 + 現金流**算出來的，失效 ③ 自動消失；只要它是從「當前 Position 的成本與市值」算出來的，失效 ③ 必然存在。**這使待決事項 3 與待決事項 1 綁在一起**：曲線的存在與否決定了哪些指標算得出來。

## 6.2 本次查證新增的一條硬事實

**yfinance `history()` 的 `auto_adjust` 預設值是 `True`**（[`yfinance/scrapers/history.py` 第 40 行](https://raw.githubusercontent.com/ranaroussi/yfinance/main/yfinance/scrapers/history.py)，2026-08-04 擷取 main 分支）。

意思是**不指定參數時，拿到的 `Close` 是還原（除權息與分割調整後）價格，不是當日實際收盤價**。這對本專案有三個後果：

1. **歷史市值會錯。** `daily_close` 若存還原價，「2023-05-10 的總資產」會用一個 2023-05-10 當天根本不存在的價格算出來。而 `CONTEXT.md` 定義 Daily Close 是「Instrument 在某個交易日的**收盤價**」。
2. **會與 Transaction 重複計算股利。** 現金股利與股票股利已經以 `CASH_DIVIDEND` / `STOCK_DIVIDEND` 記在 `transaction` 裡（`data-model.md`）。價格再還原一次 = 同一筆股利算兩遍。
3. **最陰險的一條：還原價會回溯改變。** 每次除息，過去所有的還原價都會被重新調整。若 `daily_close` 存還原價，則**今天算出來的 2023 年曲線與上個月算出來的不一樣**，而系統不會有任何提示。這與本專案已兩次否決的「靜默地錯」是同一形狀。

> **→ 這條要不要寫成硬性規則（`daily_close.close` 必須是未還原的原始收盤價，抓 yfinance 時必須顯式 `auto_adjust=False`），是本待決事項的一個具體產出。** `data-model.md` 目前只寫「`close`」，沒有規定還原與否。

# 建議的提問順序

依賴關係如下（→ 表示「必須先答」）：

```
        ┌─────────────────────────────────────────────┐
        │  ①  快照 vs 重算                             │
        │     ⤷ 但先答一個前置：R2 跨市場日曆         │
        └───────────────┬─────────────────────────────┘
                        │  （曲線在不在，決定 TWR 算不算得出來）
        ┌───────────────▼──────────────┐
        │  ③  報酬率演算法              │
        │     ⤷ 內含 R6 現金流定義      │
        └───────┬──────────────┬───────┘
                │              │
    ┌───────────▼────┐   ┌─────▼──────────────┐
    │ ④  股利處理     │   │ ⑤  大盤比較基準     │
    │   （單/雙軌）   │   │   （含多幣別）      │
    └───────┬────────┘   └─────┬──────────────┘
            └────────┬─────────┘
                     │
        ┌────────────▼─────────┐      ┌──────────────────┐
        │ ⑥  歷史價來源與回補   │      │ ②  粒度           │
        └────────────┬─────────┘      │  （相對獨立）     │
                     │                └────────┬─────────┘
        ┌────────────▼──────────────────────────▼────────┐
        │ ⑦  圖表要呈現什麼（吃前面全部的結論）            │
        └─────────────────────────────────────────────────┘
```

**建議順序與理由：**

**第 0 順位（不在七項之內，但擋著第 1 項）：R2 —— 跨市場交易日曆怎麼處理。**
台股有開、美股沒開的那天，總資產怎麼算？這不是效能問題是正確性問題，而實測顯示它讓曲線查詢從 39 ms 變成 97 ms（2.5 倍）。**不先答它，第 1 項的所有數字都不成立**，因為兩個版本算的根本不是同一條曲線。

**第 1 順位：① 快照 vs 重算。**
它是本票唯一會直接改 `data-model.md` 綱要的項目（把 `portfolio_snapshot` 從「刻意不做」搬出來）。而實算已把題目縮小成一個很具體的問題：**開頁多等 50–95 ms（本機下界），值不值得換一張會靜默過期的快取表**——注意本專案已經兩次以「漏了不會噴錯」為由否決類似設計（#10 的 `user_id`、#19 的 `transaction.status`）。
**同時要處理**：`dashboard-ui.md` §7「查詢必須夠快以支撐 60fps 拖曳」的推論已被實測推翻（拖曳不需要快查詢，只需要一次拿到 9.8 KB），該段需要修訂。

**第 2 順位：③ 報酬率演算法。**
它直接吃第 1 項的結論：**沒有每日總資產曲線就沒有 TWR**，而沒有 TWR 就沒有公平的大盤比較（第 5 項）。同時它是 issue #16 唯一被明說「留給本票決定」的項目（XIRR 要不要留，F3-5）。
**內含一個必須同時答的子題**：R6 —— XIRR 用「標的層現金流」還是「帳戶層現金流」。後者需要 `transaction-input.md` §13 明說未追蹤的交割帳戶餘額，**選了就等於開一個新的資料需求**。

**第 3 順位：④ 股利處理。**
它必須在 ③ 之後，因為「股利算不算報酬」的答案取決於報酬率用哪個口徑。而它有一個**現存的文件矛盾必須裁決**（`data-model.md` 說現金股利降低成本基礎，`tw-trading-costs-taxes.md` §4.2 說預設不變）——這個矛盾今天就在 repo 裡，本票不解就會被實作票撞上。

**第 4 順位：⑤ 大盤比較基準。**
吃 ③（要 TWR 才公平比）與 ④（自己的績效含不含股利，決定基準要不要含息）。查證工作本簡報已完成：**報酬指數的歷史序列在 FinMind 免費層可得、回溯到 2003-01-02；TWSE OpenAPI 只給當日一筆**。剩下的是選型與「序列存哪」（5.4 的三個做法，其中做法 i 不需要新表）。
**多幣別比較是這一項裡最沒有既有規格的子題**，可能需要單獨拉出來。

**第 5 順位：⑥ 歷史價來源與回補。**
它相對獨立，但必須在 ④ 之後，因為「價格要不要還原」的答案取決於股利怎麼記——本簡報已找出 **yfinance `auto_adjust` 預設為 `True`** 這條會造成重複計算與回溯改寫的陷阱（6.2）。
**這一項有最多未查證項**（R18–R23，六條），且其中 R19（債券 ETF 無歷史價來源）與 R23（`exchange_rate` 從未指定來源）是**實作前一定會撞到的洞**。

**第 6 順位：② 粒度。**
放在後面是因為它與其他項耦合最少，且實算顯示它其實是個小題：**每日一筆 = 250 列／年；盤中每分鐘 = 67,500 列／年（270 倍）**。而且盤中資料只有可選的 `quote-worker` 產得出來，這與 `realtime-quotes.md` §8 已定的「可選元件不能持有必要資料的責任」直接衝突——**這條原則可能就直接答完了這一題**。

**第 7 順位：⑦ 圖表要呈現什麼。**
必須最後，它吃前面全部。實算給出的關鍵分岔是：**個股貢獻度與資產配置變化共用同一份「標的 × 天數」矩陣（81.7 KB gzip，是總資產曲線的 8.3 倍）**，做了一個另一個幾乎免費，不做就兩個都沒有。所以真正的問題不是「畫哪幾張圖」而是「**後端要不要輸出未聚合的矩陣**」——這一問就把七項全部收斂。
