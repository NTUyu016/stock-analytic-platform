### 選項盤點

以七個候選類型逐項評估。這裡的「即時可評估」指盤中透過 Quote 觸發；「僅盤後」指只能靠 `daily_close`。

| 類型 | 資料是否已在手上 | 即時可評估 | 主要代價 / 風險 |
|---|---|---|---|
| **價格高於／低於** | ✅ Quote 有成交價 | ✅ | 最小集合。風險最低，但單靠它無法表達「跌破成本 5%」這種使用者真正在意的事 |
| **單日漲跌幅 %** | ✅ Quote + `prev_close`（1-6） | ✅ | ⚠️ **值域有硬上界**：台股 ±10%（1-7）。使用者可以設一個「漲超過 12% 通知我」的規則，而它**永遠不會響、也不會報錯**——正是本專案反覆在防的靜默失效形態。若採用，需決定是否在建立規則時就擋掉超界值（而擋的門檻本身也是規則，不得硬編碼——參照 #6「費率一律不得硬編碼」） |
| **距成本報酬率 %** | ⚠️ 需推導 Position + Cost Basis（1-13） | ✅（worker 已有推導能力，0-8） | 每次評估都要重算成本基礎；但 worker 為了算訂閱清單本來就在做同一件事，邊際成本低。**真正的風險是語意**：成本基礎會因為一筆補登的交易、一次除權息確認而改變，於是「同一條規則昨天沒響今天響了」，而使用者不會知道是門檻動了還是價格動了 |
| **停損／停利** | 同上 | ✅ | 若定義為「距成本 ±X%」，它是上一項的特例，不需獨立型別。**若要做追蹤停損（trailing stop）則完全不同**——需要記住「持有期間最高價」，那會是**唯一一個需要落地狀態的規則型別**，直接衝擊待決 2 的資料模型，也衝擊 0-7「不儲存推導值」 |
| **成交量異常** | ⚠️ Quote 有當日累積量（1-3），**但基準沒有**：`daily_close` 沒有 `volume`（1-4） | ⚠️ 只有「今天」，沒有「平常」 | **這是本項最實質的發現**：要做「爆量」就必須有歷史均量，而現行綱要存不下來。三條路都要付代價——(a) 給 `daily_close` 加 `volume` 欄位（改綱要，但成本近零且 #4 的量能比維度日後也要用）；(b) 每次評估去外部（FinMind `TaiwanStockPrice` / TWSE `STOCK_DAY_ALL`）現撈（外部相依 + 速率限制）；(c) v1 不做。另有一個語意坑：**當日累積量在早上 09:05 必然遠低於昨日全天量**，直接比會產生「每天開盤都不觸發、收盤前才觸發」的偏斜，需要按時間比例正規化——而這個正規化邏輯沒有官方定義 |
| **除權息日提醒** | ✅ 端點已在用（1-8、1-9） | 僅盤後 | 邊際成本近零（排程已存在）。**但與 `pending_action` 高度重疊**：現行設計已經會為除權息產生待確認項並在 UI 呈現。再做一條 alert 規則等於同一件事講兩遍，且兩者可能不同步。要當場釐清：警示是「提醒你未來會除息」，待確認項是「除息已發生請你確認金額」——是不是兩件事 |
| **財報日提醒** | ⚠️ yfinance `earnings_dates`（1-11） | 僅盤後 | 相依於一個**已知會靜默失效**的路徑（`lxml` 未宣告，#4 死碼缺陷 3）。若採用，`tech-stack.md` §7 的契約測試必須涵蓋它（「只驗證欄位還在、型別沒變、值不是 `None`」）。另外台股法定公布期限與美股不同（1-12），「距財報 N 天」的 N 要重訂 |

### 跨項的三個結構性取捨

1. **每多一個型別，`condition` 的形狀就多一種**，直接放大待決 2 的成本。
2. **每多一個「僅盤後」型別，就必須存在一條盤後評估路徑**——而 0-1 的硬約束**並沒有強迫你做這條路徑**：它只說「非持股標的**如果**要支援，就只能是盤後的」。若 v1 直接規定「警示只能設在持股標的」，盤後路徑可以完全不存在（除非採用除權息／財報提醒，那兩個本質上就是盤後的）。**這個選擇會決定待決 3 是「一條路徑」還是「兩條路徑」。**
3. **警示面板與最近交易共用列結構（1-14）**，型別愈雜，那一列愈難統一。這是版面對稱的支柱之一，不是可以事後調的細節。

### 仍未查證的空白

- **證交所「注意交易資訊」對成交量異常的官方標準**（幾倍量、幾日均量）——**未能查證，需人工確認**。若要對齊官方定義而非自訂倍數，需查《臺灣證券交易所股份有限公司公布或通知注意交易資訊暨處置作業要點》。
- **Fugle 免費層的 `trades` 頻道是否提供逐筆成交、以及是否提供當日累積成交量欄位**——`realtime-quotes.md` §2 只列出頻道名稱（`trades`/`books`/`candles`/`aggregates`/`indices`），**免費層各頻道的可用性未逐項查證，需人工確認**。這直接決定「成交量異常」與「未節流穿越門檻」是否真的拿得到資料。
- **`daily_close` 加 `volume` 欄位後，歷史回補的資料源與覆蓋深度**——**未能查證**（#3 只確認 FinMind `TaiwanStockPrice` 自 1994-10-01 起有價格，未逐欄確認成交量）。
- **使用者實際想要哪些型別**——本簡報無法代答。

### 選項盤點

| 選項 | 代價 | 風險（特別是「現在做錯日後會很痛」） |
|---|---|---|
| **A. 維持單表 + 裸 `jsonb`** | 零遷移成本；規則型別可隨時增加 | ⚠️ **`jsonb` 沒有 schema 檢查**：欄位名打錯、`operator` 值寫成沒人處理的字串，資料庫照收、程式碼可能靜默略過該規則——**規則不響、不報錯**。這與 #19 拒絕 `transaction.status`、#10 警告 `user_id` 是**完全同一個形狀**，而本專案已兩次拒絕它 |
| **B. 單表 + 具名欄位**（`rule_type text`、`operator text`、`threshold numeric`） | 型別安全、可加 CHECK 約束、`threshold` 可用 `numeric`；索引直接可用 | 新型別若需要兩個門檻（區間）或非數值參數（財報日的「前 N 天」）就得再加欄位，容易長成一堆恆為 NULL 的欄位。**追蹤停損若要做，`threshold` 一欄放不下**（需要另存高水位） |
| **C. 每種類型各一張表** | 每張表的欄位都精確、約束最強 | 「列出我所有的警示」要 UNION N 張表；新增型別要開新表 + 改所有查詢。對 v1 的規則數量級（個位數）是**明顯過度工程**，且與 `dashboard-ui.md` §1「警示面板是一個列表」的呈現形狀相衝 |
| **D. 混合：具名欄位承載共通部分 + `jsonb` 承載型別專屬部分** | 錢與運算子拿到型別保證，長尾參數保持彈性 | 界線在哪要當場劃清；劃錯會兩邊都不到位。**「哪些是共通的」取決於待決 1 選了哪些型別**——所以 2 必須排在 1 之後 |
| **E. 任一選項 + Pydantic discriminated union 做應用層驗證**（可與 A–D 疊加） | 已有 Pydantic（2-7），成本低；寫入前就擋掉畸形規則 | ⚠️ **應用層驗證擋不住直接進 DB 的資料**（migration、CLI、手動修）。與 DB 層 CHECK 的差別要當場講清楚，否則會誤以為已經安全 |

### 三個「現在做錯日後會很痛」的具體點

1. **`threshold` 的數值型別。** 若門檻藏在 `jsonb` 裡，它是 **JSON number = IEEE 754 double**；而本專案的錢全部是 `numeric`（2-6）。價格門檻是錢。`599.99` 在 double 下不是精確值，「大於等於 599.99」的比較會出現邊界爭議，且**不會有任何錯誤訊息**。這一項與待決 1 是獨立的，現在不決定，之後改要動所有既有規則列。
2. **`instrument_id` 是否可為空（2-3）。** 若日後要做「整個投組報酬率跌破 X%」或「不綁標的的日曆提醒」，現行綱要接不住。改成可空的代價是每個查詢都要處理 NULL 分支；不改的代價是那些規則型別在 v1 之後仍然做不了。**這是綱要層面的單向門。**
3. **`is_enabled` 是否足夠表達狀態。** 待決 4 若選「觸發後自動停用」或「冷卻中」或「已武裝／已解除」，那是**三態以上**，`boolean` 表達不了。硬塞會出現「`is_enabled=false` 到底是使用者關的還是系統冷卻中關的」的歧義——而使用者看到自己沒關的規則變成關閉，會以為是 bug。

### 仍未查證的空白

- **PostgreSQL 對 `jsonb` 的 schema 驗證能力現況**（是否有可用的內建 JSON Schema 約束，或只能靠 `CHECK (condition ? 'operator')` 這類手寫斷言）——**未能查證，需人工確認**。這會影響選項 A 的實際安全度。
- **規則數量級的上界**——使用者預期會建幾條警示？影響 C 的過度工程判定。**需當場問。**

### 選項盤點

| 選項 | 機制 | 代價 / 風險 |
|---|---|---|
| **A. 觸發後自動停用（一次性警示）** | 觸發即 `is_enabled=false` | 最簡單、絕對不會連環通知。⚠️ **使用者忘記重新啟用時，價格再次穿越就完全沒有通知，而且不會有任何錯誤訊息**——本專案反覆點名的靜默失效形態。⚠️ 也讓 `is_enabled` 語意過載（待決 2 風險 3） |
| **B. 固定冷卻期（N 分鐘內不重複）** | 記 `last_triggered_at`，未過冷卻期不送 | 需要一個落地的時間戳。**可能不必加欄位**：`notification.triggered_at` 已存在，`MAX(triggered_at) WHERE alert_id=?` 就是它——符合 4-8 的推導偏好，且**去重狀態自動與歷史一致**。⚠️ 但這讓「有沒有送出」與「有沒有寫歷史」耦合：若送出失敗但歷史已寫，冷卻期照樣生效，使用者一則都收不到 |
| **C. 遲滯／回歸重置（價格回到門檻另一側 X% 才重新武裝）** | 在領域上最正確：穿越是一個**事件**，不是一個狀態 | ⚠️ 需要一個真正的**武裝狀態**，而它**不能只從 `notification` 推導**——判斷「是否已回到另一側」要看當前價，而當前價只在記憶體裡（0-7）。這是本項唯一會強迫新增落地狀態的選項，直接衝擊待決 2。⚠️ X 的取值沒有客觀依據，且對不同價位的股票該不該同一個 X 也未定 |

**這些選項可疊加**（例如 C + D 作為封頂）。疊加的代價是狀態機變複雜，而狀態機的每個分支都需要待決 7 的歷史能重現，否則出問題時無法診斷。

### 兩個容易被忽略的點

1. **去重的粒度必須當場定義**：是「每條 alert」、「每個 (alert, 管道)」、還是「每個 (標的, 方向)」？若使用者對同一檔設了「跌破 590」與「跌破 585」兩條規則，一次快速下殺會同時觸發兩條——**去重機制若只在單條 alert 內運作，這仍然是兩則通知**。
2. **去重應該發生在「評估」還是「送出」？** 若在評估端去重，站內通知歷史也會跟著少一筆（診斷資料變薄）；若在送出端去重，歷史完整但需要 `notification` 有狀態欄（見待決 7）。

### 仍未查證的空白

- **使用者對「錯過一次警示」與「多收五次雜訊」的相對容忍度**——**需當場問**。它單獨決定 A 與 C 的優劣方向。
- **台股標的在門檻附近的實際震盪頻率**——沒有錄製的 tick 檔可算（fake provider 的錄製檔尚未存在，`realtime-quotes.md` §1 只規劃了它）。**未能量化，需實測後回填。**

### 三個需要當場定案的附帶問題

1. **管道的抽象化程度。** `notification.channel` 是一個 `text` 欄位（5-10）。若送出邏輯 `if channel == 'telegram'` 散在程式各處，換管道就是全域搜尋。本專案在行情源上已經定了「adapter 必須從第一天就可換」（`tech-stack.md` §4）與「額度也是 provider 屬性，宣告成 `ProviderCapabilities`」（`realtime-quotes.md` §2）——**通知管道是否要套同一個形狀**（例如 `ChannelCapabilities`：`monthly_quota`、`rate_limit_per_chat`、`supports_ios_without_install`），是一個現在不做日後會痛的對稱決定。LINE 的 200 則／月正是一個必須被宣告而非寫死的數字。
2. **投遞狀態往哪放（5-9 vs 5-10）。** `notification` 需要 `status`／`attempts`／`delivered_at` 之類的欄位才做得到「失敗補送」。⚠️ **要注意這裡與 #19 拒絕 `transaction.status` 的差異**：`transaction` 是事實來源，加 `status` 會讓所有既有查詢必須記得過濾；`notification` **不是事實來源**，它記的就是「一次投遞嘗試」，狀態是它的本質屬性。同一個欄位名在兩張表有完全不同的風險輪廓——這一點值得在 grilling 時明說，避免把 #19 的結論誤推過來。
3. **備援的觸發條件。** 「Telegram 失敗就補寄 Email」需要知道「失敗」——而 HTTP 200 只代表 Telegram 收下了，不代表使用者看到了。**「送達」與「已讀」的界線在哪，決定了備援會不會變成每則都寄兩次。**

### 仍未查證的空白

- **使用者是否已有 Telegram、是否願意建 bot**——#15 留言已把它標為「待本票確認」，**需當場問**。若不願意，iOS 的即時推播只剩「加入主畫面 + Web Push」一條路，並會回頭產生 #11 的加入主畫面引導需求。

### 問題的精確形狀

把 8-1 ~ 8-4 合起來，盤中一個典型的「使用者在上班、沒開網頁」情境是：

```
09:47  價格跌破停損門檻
       ├─ quote-worker：在跑（若使用者有開它）→ 看得到這個價格
       ├─ api        ：睡著（沒人開網頁）→ 沒有 LISTEN → 收不到任何 tick
       └─ 使用者     ：不在電腦前 → 站內通知即使寫了也看不到
```

於是「誰把 Telegram 訊息打出去」只有三種可能：worker 自己打、有東西把 `api` 叫醒去打、或有第三個東西在跑。**這三個選項的成本與架構影響差異很大，而且都不是 #15 一張票能單獨決定的**（#17 決定它們跑在哪）。

| 選項 | 代價 / 風險 |
|---|---|
| **A. `quote-worker` 兼任送出者（盤中）+ 既有盤後排程兼任（盤後）** | 零新元件，worker 已具備三個必要條件（8-10）。<br>⚠️ **與 8-5 正面衝突**：警示變成「可選功能」——關掉 worker 省錢，警示靜默消失。若要走這條，必須當場明確承認「**警示是即時性旋鈕的一部分**」並寫進規格，否則就是把一個必要責任交給可選元件。<br>⚠️ worker 開始持有通知憑證（Telegram token、VAPID 私鑰），它的部署面與權限面擴大。<br>⚠️ 業務邏輯常改 → deploy 頻率灌回行情連線（8-8） |
| **B. 新增第三個部署單元（notifier）** | 職責最乾淨：評估者只評估，送出者只送出，兩邊都不受對方存活影響。<br>⚠️ **推翻 `tech-stack.md` §4 的「兩個部署單元」形狀**（不是不能改，但要當場承認這是修訂）。<br>⚠️ 多一份常駐成本，與 8-9「能中途停掉」的偏好直接衝突——除非它也是排程式的（那就退化成 C 或 D） |
| **C. 外部排程定期喚醒 `api` 去排空待送佇列** | 不新增部署單元；`api` 是必要元件，責任歸屬乾淨。<br>⚠️ **定期喚醒會侵蝕 scale-to-zero 的省錢效果**——但注意量級差異：#13 否決「worker 直推 api」是因為那會讓 `api` **盤中 4.5 小時全程常駐**；每 N 分鐘喚醒一次只是短暫喚醒，兩者不是同一件事，**不應直接把 #13 的否決理由套過來**。頻率 N 直接換算成延遲上界與成本，是一個可調的旋鈕。<br>⚠️ 需要一個外部排程器，而它在哪 = #17 未定（8-6）。⚠️ 排程器本身失效時沒人會發現（#17 待決 8 的監控題） |
| **D. Outbox：評估者只把待送通知寫進 DB，送出交給「任何一個醒著的元件」** | **它把「誰評估」與「誰送出」解耦**，讓待決 3 與待決 8 可以分開決定，也讓「送出者跑在哪」可以真的留給 #17 而不阻塞本票。DB 已經是兩個單元之間的傳話筒（`realtime-quotes.md` §3），這只是把它從 fire-and-forget 升級成持久佇列**在通知這一條路上**。<br>⚠️ **要留意一個看似矛盾之處**：`realtime-quotes.md` §3 明文說「持久化佇列在這裡是有害的」——但那句話講的是**報價**（過期的 tick 比沒有 tick 更糟）。**通知不是報價**：一則「你的停損在 09:47 觸發了」的通知在 11:00 送達仍然有價值，而一則 09:47 的報價在 11:00 沒有價值。這個區分必須在 grilling 時明說，否則會被誤當成推翻既有決策。<br>⚠️ 仍然需要「有東西會醒來排空它」——D 不取代 A/B/C，它是讓 A/B/C 可以延後決定的中介層。<br>⚠️ 待送佇列積壓時的過期處理（送？不送？合併？）要定義，直接關聯待決 6 選項 C |
| **E. v1 不承諾「沒開網頁也收得到」** | 零成本、最誠實。⚠️ 這等於**否定 #7 整份研究的前提**（它假設要做外部推播），也讓待決 5 的管道選型意義大幅縮小。⚠️ 但它與本專案「前提破了就明確告訴人」的立場一致——只要在 UI 上明說即可 |

### 這一項會回頭改變其他項的答案

- 若選 **E**，待決 5 的外部管道全部可以不做，待決 4 的冷卻壓力大減，待決 6 幾乎消失。
- 若選 **A**，待決 3 幾乎被鎖定為「在 worker 評估」（因為送出者已經在那裡），並且必須接受「警示 = 可選功能」。
- 若選 **C 或 D**，待決 3 的評估位置重新自由，且待決 6 的「延遲送出」變成可行選項。

### 仍未查證的空白

- **部署平台是否提供 cron／scheduled job／定時喚醒機制、以及其計費方式**——屬 #17，**本票未查證，需人工確認**。這是選項 C 與 D 能否成立的前提。
- **`api` 從 scale-to-zero 冷啟動到能送出一則 Telegram 的實際耗時**——**未能查證，需實測**。它是選項 C 的延遲下界。
- **託管資料庫是否會自動休眠**（`realtime-quotes.md` §12 已把「資料庫是否可自動休眠」列為 #17 的題）——若會，outbox 的排空排程還得先叫醒 DB。**未定。**

## 建議的提問順序

### 依賴圖

```
        ┌─ 待決 8（誰送出）───────────┐
        │      ↕（互為前提）           │
        └─ 待決 3（誰評估）            │
                 ↑                     │
        待決 1（規則類型）              │
                 ↓                     ↓
        待決 4（去重冷卻）◀── 待決 5（管道，額度是硬限）
                 ↓                     ↓
                 └──▶ 待決 6（靜音）◀──┘
                          ↓
                     待決 7（歷史）
                          ↓
                     待決 2（資料模型 ← 是 1/4/7 的落地形狀）
```

### 建議順序與理由

| 順位 | 問什麼 | 為什麼排在這 |
|---|---|---|
| **0** | **前置定性問題（不在原票七項內）：警示失效可以接受嗎？** 具體問法：「如果某天你為了省錢沒開 `quote-worker`，警示整天不會響——這可以接受嗎？」 | 這一問同時鎖住待決 3 與 8 的可行集合。答「可以接受」→ 選項 A（worker 兼任）成立，整張票大幅簡化；答「不可接受」→ 警示成為必要功能，`realtime-quotes.md` §8「可選元件不能持有必要資料的責任」立刻生效，必須另找送出者。**這是全票的分水嶺，先問可以省下大量後續討論** |
| **1** | **待決 1：規則類型** | 它決定後面所有事的規模：型別集合決定 `condition` 形狀（2）、決定需要幾條評估路徑（3）、決定通知文案與面板列結構（7）。**先問這個是因為它是唯一可以純粹由使用者需求回答、不依賴任何技術前提的一項** |
| **2** | **待決 3：評估位置** | 承接第 0 題的定性答案 + 第 1 題的型別集合。此時「要不要盤後路徑」已經有答案（若待決 1 選了日曆型別或非持股標的，就一定要有） |
| **3** | **待決 8：誰送出** | 與 3 互為前提，但排在 3 之後，因為此時已知「評估者是誰」，才問得出「送出者能不能是同一個」。**若此處選 outbox（選項 D），可以合法地把「送出者跑在哪」推給 #17 而不阻塞本票**——這是唯一能讓 #15 在 #17 未定的情況下定案的路徑，值得優先探討 |
| **4** | **待決 5：通知管道** | 排在 8 之後，因為「有沒有送出者」決定外部管道是否有意義（若第 0 題答 E，這題直接縮小）。管道的額度（Telegram 1 則/秒、LINE 200 則/月）是下一題的硬輸入 |
| **5** | **待決 4：去重與冷卻** | 必須在 3 與 5 之後：觸發頻率取決於評估位置（未節流 vs 800ms 取樣），可承受的通知量取決於管道額度。**先定這兩個，冷卻期的數量級才有依據，否則是憑空取數字** |
| **6** | **待決 6：靜音時段** | 依賴 8（延遲送出需要有人醒著）與 1（只有盤後型別才會落在非交易時段）。**若第 1 題沒有選任何盤後型別，這題在 v1 幾乎不存在**（6-1 已結構性解決） |
| **7** | **待決 7：歷史** | 依賴 4（去重是否靠歷史推導）與 5（是否需要投遞狀態欄）。面板呈現形式依賴 1（有哪些型別要顯示） |
| **8** | **待決 2：資料模型** | **刻意排最後。** `alert.condition` 現況是「刻意的佔位，避免現在就把規則形狀鎖死」（`data-model.md` §`alert`）——那個理由到現在仍然成立，直到 1/4/7 都有答案為止。提早定形狀，等於重蹈它當初想避開的錯 |

### 三個容易被跳過、但跳過會很痛的插入點

1. **在第 1 題之後、第 2 題之前，先問「瞬間穿越門檻又彈回該不該通知」。** 它是產品判斷不是技術判斷，卻單獨決定了「在 worker 評估」相對「在 api 評估」的價值是否為正（見待決 3）。
2. **在第 4 題（管道）時，順帶問「管道要不要抽象成 `ChannelCapabilities`」。** 行情源已經因為 #13 把額度宣告化了；通知管道的 200 則/月是同一個形狀的數字。LINE Notify 被砍的前例證明管道會消失。**這是現在不做日後會痛、且成本近乎為零的對稱決定。**
3. **在第 7 題（歷史）時，順帶補三個綱要缺口**：`notification` 缺 `user_id`（違反 `data-model.md` 核心原則 5）、缺投遞狀態（#7 §8.3 明確要求）、`alert_id` 的刪除行為未定。這三個都是「現在加成本為零、日後加要動既有列」。
